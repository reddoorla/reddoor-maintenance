**The belief corrected on contact.** #1688 and the 10-24 decision treated digests like majors: a new digest branch "gets rebased every Monday and opens its PR only in a week when a second in-window run pushes nothing", with `renovate/actions-setup-node-digest` "branch present and no PR in the 10-21 dry run". On this preset a digest is never branched at all. It has no release timestamp, so under `minimumReleaseAge: "1 day"` (`timestamp-required` by default) Renovate marks it pending forever. Under `prCreation: not-pending` it then logs `Skipping branch creation due to internal status checks not met` (`lib/workers/repository/update/branch/index.ts`). The dry run's "branch present" was its `Processing N branches:` line, which names every candidate branch, created or not. reddoor-starter has no such branch.

**Why the digest half was dropped.** Round 1 ran the rules as first decided, majors and digests, on Renovate 44.181.2 at 7:32am PT. With `prHourlyLimit: 2`, lock-file maintenance opened first (reddoor-starter#210), as hoped. Then the digest opened (#211), and both grouped PRs logged `Hourly PRs limit reached` and got no branch: Renovate sorts digest ahead of patch and minor. The digest PR also carries `renovate/stability-days: pending — Updates have not met minimum release age requirement`, which never clears. That is a stop condition (a finding that contradicts the decision's premise), so it went to the operator as `decisions/2026-10-24-1436-renovate-1688-digests-and-slots.md`. The answer was (a), majors only, at about 8:00am PT.

**What `prPriority` does, read before relying on it.** `lib/workers/repository/process/sort.ts` orders branches by vulnerability alert, then `prPriority` (higher first), then update type in the order pin, digest, patch, minor, major, lockFileMaintenance. `write.ts` processes them in that order, and once the hour's count (per `branchPrefix`, from `getPrHourlyCount`) reaches the limit, `isLimitReached` stops even the branch from being created. So lock-file maintenance always came last until now. `prPriority` is accepted only inside `packageRules`. The four files are identical in 44.176.1, 44.181.2 and 44.181.3. One trap for the next probe: a dry run never applies the hourly limit (under `dryRun`, `ensurePr` skips both `isLimitReached` and the `HourlyPRs` increment, so the count never grows), so slot order needs real runs.

**The proof of the final shape.** Round 2 ran on 44.181.3 at 8:02am PT, as real runs under fresh `probe/1688-r2-*` prefixes, against the production preset with and without the two rules.

- **Majors only, no hourly limit.** The control logged `Branch created` then `Branch status pending, current sha: 1e8c08b…` for `major-vitest-monorepo`, the same for `prismicio-svelte-3.x`, and no PR. The test opened both in the same run (#217, #218).
- **`prHourlyLimit: 2`.** The control opened `all-minor-patch` (#219) and `held-minor-patch` (#220), and lock-file maintenance hit the limit. The test opened lock-file maintenance (#216), then `all-minor-patch` (#221).
- **Digests.** Every arm skipped the digest's branch.

All 13 arm PRs (#209 to #221) were drafts and are closed unmerged, and the probe PR #208 is closed too. Its `ci / ci` was red only on prettier in the probe's own generated files, left red so a push would not re-run the arms. The `probe/1688-*` branches stay, because the cloud proxy refuses branch deletes.

**The guards.** `validate.yml` now refuses three configurations. Under `not-pending`, the last rule setting `prCreation` that reaches `major` must be unscoped and `immediate`; a rule with no `matchUpdateTypes` counts. `prCreation: immediate` must not reach `digest`, whether at top level, in a `digest` block, or by a rule naming `digest` or naming no update type. And with lock-file maintenance enabled, an unscoped rule matching `lockFileMaintenance` alone must give it the strictly highest `prPriority`. The two Renovate steps, extracted and run under Node 24.19.0, passed on the patched preset; on `main`'s, the `renovate-config.json` step failed (majors guard) and the staging-flow step passed. Eighteen mutations each exited 1, and three valid variants passed; the table is in #1712.

**Review round 1** (session model) found what the first guards missed. A priority rule that also matched `minor` and `patch` tied the grouped branches with lock-file maintenance, and the update-type order put them first again, yet it passed. A later typeless `prCreation: not-pending` reverted majors and passed. Three routes to an immediate digest also passed: top-level `immediate`, a `digest` block, and a typeless rule. It also found the first text calling the next-Monday wait certain. The hourly count resets each clock hour (`getPrHourlyCount`), so a second in-window run would open the waiting PRs the same day; the wait is only usual, because the 12:00Z cron starts after the window closes on most Mondays (17:51Z to 21:12Z, measured 10-21). All of that was folded in before landing. Round 2 found a later typeless or scoped `prPriority: -1` that tied lock-file maintenance with the groups again and still passed, plus a false refusal of a harmless later scoped `immediate` major rule and of string-form `matchUpdateTypes`; all three were fixed. One nit is filed instead as #1713, because its fix belongs to the 2026-10-21 guard, which this patch does not touch.

**Honest accounting.** "Majors open the Monday they arrive" holds only in a week with a free slot. With 2 PRs an hour, lock-file maintenance and one grouped PR take the Monday run in a week when both groups refill, and the other group and any new majors usually wait a week. Raising `prHourlyLimit` was option (c), and the operator did not choose it. Separately, one slip in the container: a stray `rm -f /dev/null` in a compound command removed the device node, and a shell redirect then recreated it as a regular file. It was replaced with the real character device (`mknod -m 666 /dev/null c 1 3`) within two minutes. Only a scratch clone of `.github` failed in that window, and it was redone.
