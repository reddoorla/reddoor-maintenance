# 2026-11-04 — The deps audit stops counting majors the fleet holds on purpose (P1-98)

Where it landed: this PR (branch `claude/p1-98-deps-held-majors`), claimed in https://github.com/reddoorla/reddoor-maintenance/issues/1950. The brief is workspace `briefs/2026-11-04-p1-98-deps-audit-held-majors/worker-brief.md`; the ruling behind the `@types/node` half is workspace `decisions/2026-11-04-1736-erp-majors-base-and-node26.md` 2(a).

**Why.** All 17 maintained sites sat under the cockpit's Watch as "N packages a major behind" (`pm-cockpit` printed `watch=17` at 9:49am PT). Of 59 package-site entries in `site_health.deps_behind_packages`, 18 were `typescript@6` and 17 `@types/node`. TypeScript 7 is held by the org preset's `allowedVersions: <7.0.0` because `svelte-kit sync` crashes on it, and type definitions follow the runtime, so neither is drift anyone is meant to act on. They hid the entries that are.

**The rule.** A major-behind package is held, not behind, for one of two reasons only. (1) The preset caps it, `latest` is outside the cap, and the site is on the newest major the cap allows; only `typescript` is eligible. (2) It is `@types/node` and its major equals the site's runtime major, from `.nvmrc`, else `engines.node` when that pins exactly one major. Anything unknown counts.

**Read, not mirrored.** The preset is fetched once per process from `raw.githubusercontent.com`, and only for a site whose own Renovate config extends it. A mirror would have needed a disagreement test that reads the preset over the network anyway, and between maintenance CI runs a lifted cap would go on holding. Reading it means a lifted cap stops holding the next night. The range is evaluated by `pnpm view 'typescript@<7.0.0' version --json`, so npm's semver does the work and no dependency was added (the lockfile is the dep worker's today, reddoorla/reddoor-maintenance#1944).

**Held stays visible** in a new `site_health.deps_held_packages` column, written beside `deps_behind_packages` under the same guard and stamp. A log line would last only as long as Actions keeps it, and the column shows the entries clearing when Node 26 lands.

**Measured.** The live preset read gives `typescript → <7.0.0`; the registry's newest allowed is 6.0.3; `typescript@6` holds and `@5` does not. Projected onto today's rows, assuming runtime 24, the entries drop from 59 to 28. Vineyard Custom Homes, Revogen and 1836dig leave Watch.

**Beliefs corrected on contact.**

- **"35 held" was 31.** Four sites (LA Homelessness Youth, LA Homelessness Initiative, Sonder, CalTex) run `@types/node@25` on Node 24. The brief's own rule, which mutation 2 pins, counts those: types ahead of the runtime are drift, and the fix is to put them back on 24.
- **GitHub code search said 7 repos have a `.nvmrc`.** Reading the 14 site repos I could reach directly found one in every one, all on Node 24. Most sites' `engines.node` is `>=20`, which pins nothing, so `.nvmrc` carries the rule.
- **The preset holds two more packages**: `@libsql/client <0.9.0` and `cookie <2.0.0`. They are not covered, per the brief, and the operator decides. Neither appears in any site's list today: `@libsql/client` is 0.x, which `majorOf` never counts as a major behind.

**Mutations.** The brief's four each turned tests red: dropping the cap check (2 red), `>=` for `===` on the runtime (1), unreadable runtime as held (2), and the reader's cap changed to `<8.0.0` (5).

**Review round 1 was dirty: two majors, plus test gaps the tests lens rated major.** Each was fixed with a test that is red without its fix.

- **An `.nvmrc` alias passed as a hold.** With `lts/*`, `lts/jod` or `node` in `.nvmrc`, the code fell back to `engines.node` and held `@types/node@24`. But the alias still decides the runtime: `lts/jod` is 22, and `lts/*` is 26 since October. `engines.node` is now read only when `.nvmrc` is missing or blank.
- **One failed preset fetch, cached, would have put `typescript@6` back on all 17 sites for a night.** The fleet runs as one process (`fleet-security.yml`: `--concurrency 1`). The fetch now tries three times, only a good read is cached, and an unread preset prints `DEPS_PRESET_UNREAD`.
- **The preset's rule order and the site's own rules were not read.** A later rule, or a site rule, could lift the cap while the audit still held the package. Rules now apply in Renovate's order, preset then site, and the last cap wins. A rule that could reach the package any other way (`matchDepNames`, a glob or regex, an exclusion, a narrowed rule) makes the cap unknown, so the package counts.
- **The tests lens ran 29 mutations; 9 survived.** The gaps were the `extends` repo and file checks, the config file Renovate reads (`.github/renovate.json`, `package.json`'s `renovate` key, an unparseable first file), rule order, exclusions and registry order. Each survivor now has a test. My own first registry-order test could not tell sorted from unsorted, which a mutation showed; it was rebuilt so the wrong pick changes the verdict.

**Review round 2 was dirty too: one critical and three majors, all one belief.** Round 1's fix asked whether a rule _mentions_ TypeScript. That is the wrong question, because a Renovate rule with `allowedVersions` reaches every package it does not rule out. The audit held `typescript@6` under `<7.0.0` in each of these cases, even though Renovate would offer 7:

- a later rule matching on `matchDepTypes`, `matchManagers` alone, `matchPackagePatterns` or `matchPackagePrefixes`;
- a rule with no matcher at all;
- a second preset in the site's `extends`;
- `ignorePresets`;
- `packageRules` nested under a manager.

The check is now the other way round. A rule is ignored only when it carries an exact-name list without TypeScript in it. Every preset the site extends is read in Renovate's order, and nested presets are followed. Builtins count as rule-free. A preset outside `reddoorla/.github`, an unreadable one, `ignorePresets` or nested rules each leave the cap unknown.

Live, 1836dig (which also extends `renovate-staging-flow`), Vineyard Custom Homes and reddoor-website (which has its own `satori` rule) all still hold `typescript <7.0.0` at runtime 24.

**One round-1 fix was reversed on the production lens's evidence.** Round 1 stopped caching a failed preset read. But the fetch now retries itself, so not caching made every site retry: about 51 s each, roughly 14.5 min a night. A failed read is now kept for the run, and `DEPS_PRESET_UNREAD` prints once.

**The tests lens found that the end-to-end test passed with the injected reader ignored.** It fetched the live preset, whose cap happened to match. An injected preset with no cap now pins the injection. The minors that need a workflow change or a design call are https://github.com/reddoorla/reddoor-maintenance/issues/1953.
