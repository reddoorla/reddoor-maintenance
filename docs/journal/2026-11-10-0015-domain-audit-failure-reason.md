# 2026-11-10 — The domain audit says why it failed (the MSOT blip of 11-09)

Landed in this PR (`fix(audits)`), from the workspace brief `briefs/2026-11-09-msot-domain-blip/worker-brief.md`.

**What happened.** The dispatched `fleet-lighthouse` run 42711182637 (2:21 to 2:46pm PT on 11-09) logged `domain warn msot` with the summary `resolved, no usable TLS cert`, and the cockpit raised MSOT to Needs you as Broken. In the same run MSOT's `browser`, `lighthouse`, `function-health` and `netlify-deploy` audits passed, and every other site's domain check passed. The reason was thrown away: `certValidTo` turned every `error` and `timeout` event into the same `null`. So the cause of that one failure **cannot be named from a recorded code**. This PR makes sure the next one can.

**What the evidence rules out** (raw output from two throwaway runner probes on `claude/msot-domain-probe`, runs 42723268143 and 42723507282, 3:47 and 3:49pm PT, never merged):

- **The instrument first.** On the runner, the production `certValidTo` logic with the reason kept returned `ok` for roalson.com 40 of 40 times, `ENOTFOUND` for `does-not-exist.invalid`, `CERT_HAS_EXPIRED` (also `ECONNRESET` and one `timeout`) for `expired.badssl.com`, and `timeout` at 10,001 ms for the unroutable `10.255.255.1`.
- **IPv6 (hypothesis 1): ruled out.** MSOT's apex has no AAAA record (`ENODATA` on the runner, empty from dns.google). It has two A records, `99.83.231.61` and `75.2.60.5`, where Roalson has only `75.2.60.5`. Both are AWS Global Accelerator addresses, and both serve the same valid cert: 5 of 5 verified handshakes each, `openssl s_client` `Verify return code: 0`, and curl `200` through each.
- **The cert: not the cause.** The cert served now is Let's Encrypt **YE1**, `valid_from Nov 3 05:43:49 2026 GMT`, expiring 2027-02-01. Netlify's SSL record shows it was renewed 2026-11-03 06:42 UTC (11-02 10:42pm PT). The brief's "YE2, expiring 2026-12-03" was the previous cert; crt.sh had not indexed the new one yet. So the 11-09 run saw a cert a week old, and no rotation happened during the run.
- **A deploy at that moment (hypothesis 2): unlikely.** MSOT's production publishes on 11-09 were 1:34pm PT (#112) and 2:03pm PT (#188); its audits ran from 2:34:51pm PT, half an hour later.
- **A 10 s timeout (hypothesis 3): consistent with the timing, not proved.** The five audits for a site run concurrently, and the run log stamps each completion. For every other site that night, three audits finished within 3 s. MSOT's third finished at **10.07 s**: about 70 ms of DNS plus the 10 s socket budget. **Belief corrected:** I first read that as proof, but on 11-07 (run 42454234669, 10:19pm PT) MSOT also had a 10.0 s completion while domain **passed**. That one was `function-health` timing out on `/health` (`skip … unreachable`). On 11-09 function-health passed, so the 10.07 s step was most likely the domain socket timing out. That is still an inference. So MSOT's edge has stalled for about 10 s on two of the last three nights, once on HTTP and once (probably) on TLS.

Repeated probing found no failure: MSOT 42 of 42 `ok`. The blip does not reproduce.

**The change.** `checkDomain` returns `reason`. The summary becomes `did not resolve (dns ENOTFOUND)`, `resolved, no usable TLS cert (tls ECONNRESET)`, `… (tls timeout after 10000ms)`, `… (tls DEPTH_ZERO_SELF_SIGNED_CERT)`, `… (tls no certificate returned)`, `… (tls certificate expiry unreadable)` or `did not resolve (invalid URL)`. `details.reason` carries the same text, and the run log prints the summary. A timeout is its own `DomainTimeoutError`, so it can never read as a DNS failure. `defaultDomainDeps` takes optional `port`, `timeoutMs` and `ca` so the tests can drive the **real** TLS code against local servers: a trusted cert (the positive control), a self-signed one, a peer that never answers TLS, and a refused port. `rejectUnauthorized: true` is unchanged. The reason is not stored in Turso; that would need a migration, and the brief asked for it in the summary, details and log.

**Mutations.** Dropping the reason from the summary turned 6 tests red. Mapping a timeout to "did not resolve" turned 2 red. **`rejectUnauthorized: false` alone first turned nothing red**: the belt-and-braces `socket.authorized` check still fails an untrusted cert closed, so the behaviour test passed. A spy test now pins the flag itself. With the flag off and the guard removed too, the untrusted-cert test goes red as well.

**Left to the operator.** One failed run still raises a critical Broken. Whether that should take two runs, or a retry inside the audit, is his call. It is asked in the workspace decision file `decisions/2026-11-10-0015-domain-broken-after-one-run.md`.
