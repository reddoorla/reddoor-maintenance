## 2026-10-14 — Williamson GA4 and Search Console wired, and the Google console steps become worker steps (P1-51, williamson-homes#39, williamson-construction-co#29)

Follows 2026-10-14-1646 (the launch-check gate). The operator created both GA4 properties and verified both Search Console domains himself, then granted the service account's domain-wide delegation the four write scopes asked for, "for new sites going forward". Before the grant, minting a token as the GA subject was refused (`unauthorized_client`) for `analytics.edit` and `analytics.manage.users`. `webmasters` and `siteverification` were already allowed, which nobody had written down. After the grant, all four mint.

**Every ID was checked against a second authority before it was recorded.** The Admin API lists one web stream per property, and each matches the `G-` ID the operator sent. Both properties answer the Data API, and both Search Console domains answer the lookup `fetchSearch` runs. The worker then wrote `ga4_property_id` and `search_console_property` through the site mirror.

**`reports@` could not read Search Console, and two steps fixed it.** The container's `GA_SUBJECT` is `tucker@` only, so every earlier `ok` proved access for tucker. With delegation, a read as `reports@reddoorla.com` showed GA fine, but both Search Console domains refused it. The Search Console API cannot add a user. The Site Verification API can add an owner to a resource the acting account owns: tucker owns both domains, and Homes also carries `admin@williamson-construction.com`. After the owner was added, the lookup still refused. It passed, reading `siteOwner`, only once `reports@` had added the property to its own list (`PUT sites/{site}`). An owner is a stronger role than the runbook's "user". It is the only role the API grants, and it is revocable.

**The tag needed a dependency bump nobody had listed.** Both sites pinned `@reddoorla/maintenance` 0.97.0, and `initAnalytics` first ships in 0.102.0, so both went to ^0.108.0. The first bump used `pnpm add -D` and moved the package into devDependencies. That was caught in the lockfile diff and redone, because the hook runs in the client bundle.

**The `analytics-tag` recipe refused Homes on a comment** (#1379). The starter's privacy port explains its GA switch in a JSDoc block containing "``finds an `initAnalytics(` call``", and the recipe's scan read that as an existing call. The comment was reworded in the commit that turns the ahead-of-tag flag off. Every site that gets the privacy page before the tag, the order the runbook prescribes, will hit this until the scan strips comments. The recipe cannot edit SvelteKit's own `kit.csp`, so the hosts it prints were added by hand, as on 1836dig and 29 Navy.

**Proven before asking for a merge.** On both deploy previews the CSP meta carries `googletagmanager.com`, `*.google-analytics.com` and `*.google.com`, and the client bundle carries the site's own `G-` ID. The tag stays inert off the production host, so a preview cannot show it loading. Each privacy test that pinned the pre-tag state now asserts that GA4 comes from the tag. Removing `src/hooks.client.ts`, or turning the override back on, turns them red. `launch-check` reads 6 of 8 `ok` on both sites. `ga-tag` and `privacy` are the two lines left, and the merges fix them.
