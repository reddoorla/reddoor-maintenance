This is the data half of P1-87's list items 6 and 7 (engaged visits, and Search Console clicks and impressions); the tiles and trends are PR 7.

Each night's row now carries the fleet's engaged visits for the 30 days ending on the night against the 30 before, Search Console's 28 days ending 3 days earlier (its data lags), a per-day series for each, and each site's totals. The series rides in the row, so the first night already holds the past 60 days, and no earlier row is ever rewritten: backfilling one day per older row would have written into rows that hold nothing else and bumped `cockpit_version` once per row. The windows come from the night, not the clock, so a re-run the next afternoon reads the same days. A read that fails is stored as unmeasured with its reason, never as 0.

**Beliefs corrected on contact:**

- **A failed night is not a null block.** Round 2 kept the series on "the newest row whose traffic block has a value". But the writer stores "GA not configured" and a night where every read threw as `{ value: { visits: { value: null, reason }, search: { value: null, reason }, sites } }`: a non-null block whose halves are null. So the failed newest night took the slot, and the good night before lost its series, which is exactly what the rule was meant to stop. The test that "proved" it hand-wrote the failed night as `{ value: null }`, a shape the writer never stores. Round 3 placed each half's series on the newest night that read that half, and built the failed rows with the real `readTraffic`. Round 4's correctness lens then ran 10 writer shapes as all 100 newest/older pairs, and 3,000 random blocks with 0 throws.
- **`process.exit` right after the work is not free.** Round 2 added it so a stalled socket (google-auth-library's token POST has no timeout) cannot hold the job to its 15 minutes after the row is written. Round 3's security lens measured that on a pipe, a 200,000-byte write followed by that exit delivered 65,536 bytes and no `FLEET_DAILY_RESULT` line, because Node's stdout goes asynchronous once the 64 KB pipe buffer fills. The exit is now a 10 s unref'd fallback timer: a normal run exits when its event loop empties and flushes everything, and only a run held open by a stalled handle is cut off. Round 4 checked 8 cases (normal, 200 KB stdout, a failure with a 200 KB stack, a held interval, a held socket, and combinations); each exited with its code, every byte delivered. No test pins the exit yet, and a 0 ms timer survives (filed).
