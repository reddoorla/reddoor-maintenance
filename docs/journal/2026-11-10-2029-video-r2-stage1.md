# 2026-11-10 — Video on R2, stage 1: the library half (player profile, relay, encode, captions, stuck check)

Landed in this PR (`feat(video)`, branch `claude/video-r2-stage1`, minor changeset). It was built over three sessions, each handed off at a seam. The workspace keeps the briefs (`briefs/2026-11-10-video-r2-stage1/`), the decisions (`decisions/2026-11-10-1741-…`, `-1801-…` and `-1912-…`) and the session journals. The site half is reddoorla/reddoor-website `claude/video-r2-stage1`, which waits for this release.

**Why.** The operator chose to build on R2 rather than buy Mux. Prismic's Free plan locks a repository after 100 GB a month, and until now a staff member had to run `reddoor-maint video` by hand and upload four files, which a client cannot do. With this pipeline a client editor uploads one file to Prismic and publishes, and everything else follows without a hand step.

- A webhook relay checks the secret, classes each new video `background` or `player` by its slice, and dispatches the site's `video-encode` workflow.
- The workflow encodes the video. A player keeps its AAC audio, which the old recipe's `-an` stripped. A player also gets Whisper captions.
- It uploads the files and a per-video `manifest.json` to R2, then rebuilds the site.
- An hourly stuck check opens a `video-pipeline` issue when a video has sat on its Prismic file for over an hour. This matters because Prismic disables a webhook after 5 failures, so a dead pipeline would otherwise be silent.

**Review: five rounds on Opus, four dirty, the fifth clean.** Most of the majors were one defect, fixed in one place and still open in a second.

- Round 2: a background encode overwrote a player's manifest, which dropped its captions and audio.
- Round 3: the same overwrite in its concurrent form. Both runs read 404 at the start, and the slow VP9 webm makes the background run finish last. Encode now re-reads the manifest just before the PUT.
- Round 4: one site name, two rules. `videoKey` slugified the site, so a relay configured with `reddoor_website` answered Prismic `200` and dispatched `reddoor-website/…`, while encode and stuck refused `--site reddoor_website` with exit 2. Every publish would have reported success, and every encode would have failed. There is now one `SITE_NAME` rule, `[a-z][a-z0-9-]*`, used by `videoKey`, the relay (`500` after the secret check), encode and stuck.
- Round 4 also bounded the master download: a redirect is an error, and a stalled download gives up after 10 minutes. Round 5 checked that Prismic's real file CDN (`<repo>.cdn.prismic.io`) answers a range GET with 206 straight from CloudFront, with no redirect, so the stricter fetch costs nothing.
- Round 5's minors that only needed text were folded in: the README now documents `--force` and the site-code entry points, and the stuck advice names the workflow's `force` input. One minor needed a new test, so it is filed as reddoorla/reddoor-maintenance#2028: a failed download prints only "fetch failed".

**Beliefs corrected on contact.**

- The brief said dropping `-c:a` strips audio. It does not: ffmpeg's mp4 default audio codec is AAC. M1 is caught only at the argument level. M5 is the mutation that really strips audio.
- The relay first used `repository_dispatch`, which needs a Contents: write token. That token would sit in Netlify env with write access to a public repo. The relay now uses the workflow-dispatch API, which needs Actions: write only.
- The pilot is reddoorla.com, not Williamson. Williamson has no player slice, so it could never show captions.
