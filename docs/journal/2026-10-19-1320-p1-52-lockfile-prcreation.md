## 2026-10-19 — Lock-file maintenance opens no PR because `prCreation: not-pending` can never pass for it inside the window; the fix is a proven `.github` patch (P1-52, Operator decisions 130)

P1-52's worker. The Monday PM pass found that no lock-file PR had opened in any of the 15 maintained repos since 2026-09-15. It guessed the cause from the preset's own 09-21 note: the 25-hour `prNotPendingHours` fallback. The guess was right but incomplete, and it is now proven by Renovate's log rather than read from the config.

**The instrument.** A cloud session cannot run Renovate's GitHub platform, because the proxy refuses GraphQL. So the probe was vida-legacy-foundation#99's shape, moved to erp-industrial (#72, draft, closed once read). It ran the fleet's action (v46.3.1, Renovate 44.151.2) with the reddoor-renovate token, `dryRun: full` and `LOG_LEVEL: debug`, in two arms. Both arms kept the production schedule, because the run was at 13:15Z on a Monday, inside the window. That makes this probe closer to production than #99, which had to override the schedule.

- **`control`, the preset alone:** `Branch status is yellow - checking timeout`, then `Branch is 10 hours old - skipping PR creation as prNotPendingHours is set to 25` on `renovate/lock-file-maintenance`.
- **`immediate`, plus `lockFileMaintenance.prCreation: "immediate"`:** `DRY-RUN: Would create PR: chore(deps): lock file maintenance`.
- **Mutation 2 (nothing else changes):** the arms' sorted INFO/WARN action lists were 11 and 12 lines, and the diff was that one line. Five majors were "Would create PR" in both arms.
- **Mutation 1 (the control arm itself):** with the change reverted, there was no lock-file PR. The control arm also passed its own known-good check: the same run would create the five majors' PRs, so a "no PR" was not a dead instrument.

**What the guess missed: there are two blocking paths, not one.** In Renovate 44.151.2's source (`workers/repository/update/branch/index.js`), a run that pushes a commit to a branch with no PR returns `pending` before `ensurePr` whenever `prCreation` is not `immediate`. The 09-21 note describes this as "Renovate's ordinary early return". The weekly refresh nearly always changes the lockfile: ERP's branch was rebuilt at 10-12 03:25Z and again at 10-19 02:30Z. So each Monday's first run is blocked by the early return. Every later in-window run is blocked by the 25 h timeout, because the branch is at most 18 hours old inside the window. Outside the window Renovate logs `Skipping PR creation out of schedule`. The dry run cannot show the early return, because it commits nothing (`commitSha` is null), so that path is a source read, not a log line. `immediate` removes both paths.

**Why the 09-21 fix missed this update type.** `internalChecksAsSuccess` only changes how `renovate/*` statuses are counted. A lock-file branch has none, because `minimumReleaseAge: null` gives it no stability status. With zero statuses and zero check runs, the GitHub platform's `getBranchStatus` returns yellow whatever the option says. ERP's branch matched that exactly: combined status `pending`, `statuses: []`, `check-runs: 0`. The 09-21 note said lock-file PRs "kept appearing" in August (gallerysonder#88, 08-31). That fits the mechanism: a week with no lockfile change leaves the branch older than 25 h on the next Monday.

**espada is a third face of the same thing.** Its branch was not rebuilt today (`d2e0bb06`, still from 10-12), and espada#49 lists it under **Rate-Limited**. Its 02:03Z run updated `all-minor-patch` and opened two majors, which spent the hourly commit limit. Its next in-window run will rebuild the branch and hit the early return. This was read from the Dashboard and the info-level log, not from a debug run.

**Safety does not move.** With `immediate` the PR opens in the run that pushes, but the merge still goes through Renovate's automerge check on a later run. That check needs a green branch status, and zero checks read as yellow until CI registers. The base branch's required check (the preset's invariant 3) holds it as before. Preset invariant (1) asks whether an option can leave a PR pending at creation time. This one removes the pending wait.

**Shipped as a patch, not a PR.** The brief asked for a PR in `reddoorla/.github`, and no route from a cloud session reaches it. `add_repo` refuses repository names that start with `.`, the git proxy refuses the push (403, "not in this session's authorized repository set"), and the GitHub connector refuses even a read. So the change is `docs/patches/2026-10-19-github-renovate-lockfile-immediate.patch`, which applies cleanly on `b3e549e`, as the 09-29 and 10-12 changes were. It holds the one key and a description note. It also adds a `validate.yml` check: it refuses `not-pending` (or `status-success`) with lock-file maintenance enabled unless lock-file maintenance has `prCreation: immediate`. Run locally on all three validate steps, the check was green with the change and red on today's preset, with the key removed, and with the key set to `not-pending`. The dry run proved a repo-level override, not the preset file. The two are the same config, since `lockFileMaintenance` is a mergeable object, and the resolved config in the log showed the override merged over the preset.
