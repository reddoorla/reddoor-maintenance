# 2026-11-17 — P1-87 PR 5a: the nightly audit bar on the overview's first screen

Landed in [reddoorla/reddoor-maintenance#2083](https://github.com/reddoorla/reddoor-maintenance/pull/2083). The plan is the workspace's `plans/2026-11-16-p1-87-overview-reorg/pr5-nightly-bar-ticker-plan.md`, and the round briefs are `pr5a-round{1,2,3}-fixes.md` beside it. The bar is P1-87's list item 1 (the nightly audit as a progress bar) and motion item 1 (it runs on the clock).

The bar shows the nightly audit's eight steps in run order, then the wait to the next run. Mid-run it shows what the run has done so far, which has no direct signal. The night's `fleet_daily` row is written only when the whole run ends, so mid-run the only evidence is site stamps. Those come from five of the eight steps. The rule (the operator's "infer from order") is that the steps run in order, so a stamping step that has stamped since tonight's start finishes every step before it.

"Has stamped" took four review rounds to get right, because the run's real facts beat the plan's:

- A site Re-test stamps the same columns as the nightly. So a step counts only once two maintained sites carry its stamp from tonight; or one, when the last night that counted it reached only one; or when only one site is in our care.
- Stamps after the window's end do not count.
- October is PDT, so the start is 11:07pm, not 10:07pm.

During the run window the page re-reads its data about every 2 minutes, and once the view has gone stale.

**Defects the rounds found, named:**

- **Round 1 (8 majors in all):** two came from stamps that are not the conductor's: a site Re-test, and the conductor moving on while a late step keeps running.
- **Round 2:**
  - The 2-minute re-read was measured from when a read settled, not from when it began. A real `invalidate` takes time, so reads landed at minutes 1, 4, 7. A fake that resolved at the same instant had hidden it.
  - The view's stale time and the distinct-site rule were unpinned.
- **Round 3:**
  - The browser's repeating interval fires a few ms late by a varying amount. Two ticks nominally 120 000 ms apart can measure 119 99x, so a re-read was skipped about half the time; with jitter, reads landed at 1, 4, 6, 8. The threshold is now 90 s.
  - A base `none` border placed after the forced-colours block beat that block's 2px by cascade order, so forced `none` drew 1px. A CSS-text pin passed throughout; only a browser measurement caught it.
  - Round 2 removed the forced-colours browser test's `if (marker !== null)` guard without seeding a recorded night. The test would then have failed for every run from about 10:07pm to 3:07am PT. The seed now writes the bar's own run night, and the repo's `REDDOOR_TIME_TRAVEL_DAYS` shim proved it at 06:25Z, 08:00Z and 11:00Z, with a negative control that fails at 08:01Z.
- **Round 4:** clean on all three lenses. Its minors needing new tests are filed; the rest are folded.

**Beliefs corrected on contact:**

- **The in-flight slot and the 30 s read timeout were dead code once the gap ran from a read's start.** Round 2's mutant e12 (a late answer clears whichever read holds the slot) survived.
  - The fixer argued it was equivalent. A 2000-seed differential fuzz confirmed it: 0 differences, against 1530 of 2000 for a control mutant.
  - Round 3 removed the slot, the read ids and the timeout. A 3000-seed jitter fuzz with visibility ticks and hung reads then found reads on every other tick in every seed.
  - Overlapping reads were already reachable before, and are safe: SvelteKit's `_invalidate` drops a result whose `invalidation_token` is stale.
- **"Measure from the start" needs a fake read that takes time.** Every clock test now has one.
