# 2026-11-12 — a send run skips the browser and font installs (#2034), and the 11-11 Actions stall (#2039)

Landed in reddoorla/reddoor-maintenance as #2041 (workflow and test only, no changeset). The #2039 finding is a comment on that issue: https://github.com/reddoorla/reddoor-maintenance/issues/2039#issuecomment-6833434505. Worker brief: the workspace's `briefs/2026-11-12-cockpit/failures-worker-brief.md`.

**B, the send run.** Wednesday's 8:07am PT send run, 43055102047, died in `playwright install --with-deps chromium` on `Temporary failure resolving 'security.ubuntu.com'`, before it sent. The send needs no browser. `report --send-ready` takes the stored header from Turso and only composites a pre-rendered PNG headline onto it with sharp. The one place text is drawn is `domainSvg`, which is reached only from `generateHeaderImage` at draft time, and Chromium is imported lazily inside the draft-time shooter. So both apt steps, the Playwright install and `fonts-urw-base35`, now run only in a drafting run: `inputs.preview_site || (inputs.mode || 'send') != 'send'`. The `|| 'send'` is load-bearing. The cron fallback has no inputs, and Actions reads `null != 'send'` as true, so the plain form would have kept installing on the fallback. A mutant pins exactly that.

The test evaluates each step's real `if:` under a small model of Actions' expression rules, rather than matching the condition's text. It then asks two things of the step list. First, does any apt-touching step run before "Send approved reports" in the cron fallback or a `mode=send` dispatch? Second, do the draft, all and preview dispatches still install both before "Draft due reports"? Mutations: an unconditional install went red 2 of 11; gating on `!= 'draft'` went red 3 of 11; the null trap went red 1 of 11; and after review, an ungated `sudo apt install` step went red 2 of 11.

The fix is sized to the evidence. Over 30 days, one maintenance run failed at an install step, out of about 2,370 runs of workflows that install with `--with-deps` (ci retries its install, so ci's share is a floor). That is why this is two `if:` lines and no retry machinery. A `mode=all` or preview run still installs before it sends, so an apt outage can still stop one of those; the 16:07Z send clock dispatches `mode=send`, so the daily send no longer depends on Ubuntu's mirrors.

**A, the stall.** It was GitHub's outage, not our billing. githubstatus.com's incident history has a critical incident, "Impact across multiple GitHub products including Actions, Pages, and Copilot products". It was declared at 12:48pm PT, mitigated at 1:07pm PT and resolved at 1:21pm PT, and a Webhooks incident ran from 12:22 to 12:26pm PT. #2039 was filed at 1:24pm PT, three minutes after the resolution, with only the front page in view. Corrected belief: "githubstatus said operational" was a read of the present-tense page after the fact. The incident history (`/api/v2/incidents.json`) is the instrument for "was there an outage".

Billing is ruled out by a negative control. Maintenance is public, its runs bill 0 ms (`/timing`), and it stalled all the same.

The runs that stayed queued for hours are a different shape from a slow queue. 43096788479 (ci on #2038, created 12:33:49pm PT) still read `queued` with **0 jobs** and an `updated_at` 22 hours stale at 11:13am PT Thu. Its check suite has 0 check runs. GitHub created the run record and never created its jobs, so "backlog processed" never reached it. That is consistent with the 409 and 403 the Vineyard and website sessions recorded, and with a new `pull_request` event being the only cure. A smaller sign came earlier: daily-reports 43094711201's run was finalised 43 minutes after its only job ended (`run_duration_ms` 2,695,000). Run bookkeeping was lagging at 12:16pm, 32 minutes before GitHub declared anything.
