## 2026-10-19 — Bake-off row 6: dependency bumps (`pnpm update`) on reddoor-starter, every arm at the ceiling (P1-58)

Row 6 of reddoorla/reddoor-workspace#1 asks whether a cheap model can do a dependency bump: run `pnpm update` on a site repo, install, run the checks, report the resolved versions and what failed. The step is mechanical and a script can compute its gold, so this adds `scripts/model-bakeoff/tasks/pnpm-update.mjs` and runs it on reddoor-starter at `2a9f493`.

**The registry is frozen as a pnpm metadata cache, not by timing.** The brief allowed either a gold taken at the same minute or an offline store. `pnpm update --offline` with `XDG_CACHE_HOME` pointed at a copy of the cache an online `pnpm update --lockfile-only` filled resolves byte-identically to the online run (15:50Z, `cmp` equal), and with an empty cache it fails and leaves the lockfile untouched: the negative control. `snapshot` tars the repo (`git archive`) and that cache, records the sha and minute, and installs once so the shared store holds every tarball. The freeze is therefore only as good as this container: the offline runs also need the shared store and pnpm 12.5.1 in place, which the truth's offline install at `prepare` proves for that moment.

**The bump breaks the starter's `svelte-check`, which made the task sharper than the brief assumed.** The brief described the gold as "the resolved-version map plus the repo's checks passing". At the pin all four checks pass (lint 14 s, check 10 s, build 17 s, unit 60 s; 588 tests). After a plain `pnpm update`, `check` fails with 48 errors, all "Cannot find name 'process' / 'node:fs'": `@types/node` was only ever arriving transitively, and the updated tree no longer pulls it. Lint, build and the unit tests still pass. Rather than pick a pin that hides it, the gold is "check fails", which tests whether an arm reports a red check honestly. The starter itself is out of this item's scope; a Renovate lock-file refresh on that repo would hit the same failure, and it needs `@types/node` as a direct devDependency.

**pnpm 12 writes the lockfile as two YAML documents.** The first is the package manager's own environment (`packageManagerDependencies`, the `@pnpm/exe.*` binaries), the project is the last. `prepare` died on `js-yaml`'s `load` ("expected a single document") before the parser took `loadAll().at(-1)`.

**Five review rounds, each dirty, and almost every finding was the instrument, not the models.** The harness was built for extraction, so the first slice added an `observe(work, structured)` hook to score what an arm left on disk. Each 3-lens round then found a way the score could be right without the work, or wrong for an honest arm:

- Round 1: 101 of 110 checks were read from disk and identical for any arm that ran one command, a no-output arm went to the referee, and a harness-computed boolean went to a referee who could not see what it measured. Fix: score the report per package, the lockfile as one item, and make every collection `mechanical` (a new per-collection flag in `lib/score.mjs`) so nothing reaches a referee.
- Round 2: "did the arm run the check" was inferred from transcript command text. Its first real input showed it was wrong: every arm ran `for s in lint check build test:unit; do pnpm run $s …; done`, and the literal matcher scored all eight 105/113. Widening it to loops still credited `echo pnpm run build` and missed `pnpm -C`. Fix: the prompt prescribes `<work>/logs/<script>.log` and `.exit`, and the evidence is read from disk. That changed the prompt, so run2 (all 8 agents 113/113 under round-1 scoring) was dropped and run3 run fresh.
- Round 3: scoring both the claimed verdict and the exit code against the truth counted one fact twice and charged an honest arm for a timeout under load. Fix: score `reportsOwnRun` (claim against the arm's own exit code).
- Round 4: with only that, a false pass scored perfect whenever the exit file said 0 (`| tee` records tee's code). Fix: a one-sided `noFalsePass` against the truth (load can fail a passing script, never pass a failing one), with the reference passed to `observe`, plus pnpm's failure line overriding a 0.
- Round 5: a headline `pass: true` beside `failed: ["check"]` still scored perfect, and the failure regex matched execa's "Command failed with exit code 1: <cmd>" inside a passing test log. Both are fixed on the branch, but round 5 was the last the rules allow, so the PR went to Operator decisions instead of a sixth round.

No arm in run3 did any of those things. Every fix after round 2 changed scoring only, so run3's arms stand; its `truth.json` was recomputed from the same frozen input twice, as the scored fields changed, and packages and disk were identical to the `prepare`-time truth each time.

**Result [M].** run3 (`wf_c1f38f8d-9d2`, snapshot 16:26Z): gold Opus 5.5 `high`, Haiku 5.5 `low` ×2 and `medium` ×2, Sonnet 5.5 `medium` ×2 and Opus 5.5 `low` ×1 all scored 117/117 (packages 100, disk 4, checks 13). Each transcript shows exactly one `message.model` and `effort`, equal to what was asked. A second authority agrees: all eight lockfiles have sha256 prefix `3ba017dbcc49`, the truth's, every arm's exit files read lint 0, check 1, build 0, test:unit 0, every `check.log` reads `COMPLETED 4668 FILES 48 ERRORS`, and no transcript mentions the truth. Mean cost per run: Haiku `low` $0.0132, Haiku `medium` $0.0128, Sonnet `medium` $0.2388, Opus `low` $0.4956, gold $0.7984. The workflow started the agents in pairs about three minutes apart on 4 cores.

**Honest accounting.** It is a ceiling: the run bounds an error rate on this recipe and ranks nothing, and 104 of the 117 checks follow from the one dictated command. The judgment step was not scored. Only the gold established that the `check` failure came from the bump (it diffed `@types/node` between the lockfiles); every cheaper arm named the symptom and said in `unverified` that it had not established the cause. The Opus `high` gold used the `Monitor` tool, outside the allowlist, to wait on its own check loop; the arms are scored against the script truth, so it does not touch them, but `score` reports it. An earlier draft of the backlog line called Haiku `low` "the cheapest"; by mean cost the two Haiku settings are the same within noise.
