## 2026-10-20 — Operator decisions 97(g): a monthly copy of the encrypted Turso backup in Dropbox (reddoorla/reddoor-maintenance#1549)

Until now the nightly backup lived in one place: a 30-day Actions artifact. If GitHub lost or locked it, there was no other copy. The operator chose Dropbox, with the folder `/Reddoor/Backups/turso`, one `turso-YYYY-MM.sql.gpg` per month, and nothing ever deleted automatically. `fleet-db-backup` now makes that copy on the first run of each UTC month, or on a dispatch with `dropbox_copy: true`, and only from `main`. The copy goes through `scripts/dropbox.mjs`. It runs after the artifact upload and is `continue-on-error`, so it can never turn the backup red. It passes only when two of `dropbox.mjs`'s own lines appear: the account line naming the team space, and the hash-matched `ok` line for that month's file. The file it copies is the same `dump.sql.gpg` that the Encrypt step already decrypted back and re-verified. The plaintext was deleted before the copy step and is never named in it.

**It is not live yet.** The three `DROPBOX_*` Actions secrets are the operator's to add (red tier). Until they exist, a copy night prints a warning naming them and skips. The first proof will be a dispatch on `main` with `dropbox_copy: true` after he adds them.

Measured from this session with the same app credentials: `dropbox.mjs check` reported a team-space account (team Reddoor Creative, root namespace distinct from the home namespace) with `files.content.write` and `file_requests.write` granted. The team root holds `/Clients`, `/Marketing`, `/Processes & Procedures` and five more, but **no `/Reddoor`**. The first upload will therefore create `/Reddoor/Backups/turso` as a new top-level team folder; dropbox.mjs creates parent folders silently (#1390). The brief's stop condition, "resolves outside the team space", did not fire, so this is reported rather than asked.

Four review rounds. The first three were dirty, and each found something worth more than its cost:

- **A lost month was silent.** On the first draft, if the run on the 1st went red before the copy, the copy step was skipped, nothing was filed, and the next green night closed the backup-failure issue. That month never got a copy, and nothing said so. Now the decide step runs first in the job, and the Dropbox issue also files when a copy night's run goes red or is cancelled before a successful copy. One gap remains: a 1st on which the conductor dispatched nothing at all files only the conductor's own issue.
- **The instrument could not see the main defect class.** `tracking-issue-conditions.test.ts`'s expression evaluator reads `.outcome` and `.conclusion` as one value, and every `steps.*.outputs.*` as one value. So `steps.dropbox.conclusion == 'failure'` passed every test. Under continue-on-error that expression is never true, and the failure would never file. Reading the wrong step's output passed the same way. The two Dropbox issue conditions are now pinned verbatim, with an evaluated table beside them. The evaluator itself still has the blind spot. Any other workflow that keys a step on a continue-on-error step's result is exposed to it in the same way.
- **Stubs that could not fail.** The first `date` stub fell through to the real clock, so a test that dropped `-u` failed only because today is the 20th. The first `node` stub always exited 0. Both now refuse what they do not model.
- **Restoring an old copy.** A Dropbox copy can be months old, so its schema can be behind the code. The runbook forbade `db migrate` before the restore and never ran it afterwards. Step 1's Dropbox path now runs it after step 4, and explains how to decrypt a copy made before a passphrase rotation.

The four mutations the brief committed to each turned a test red: uploading plaintext, copying every night, letting a Dropbox failure fail the job, and naming by run id. So did about 25 more that the reviewers or I tried. The table is in the PR. Round 4 found only minors. Those in files the PR touches were folded in. The one outside it, `restore/` not being gitignored in a public repo, is #1558.

One local failure is not this PR's: `tests/scripts/dropbox.test.ts` "re-executes through HTTPS_PROXY" fails in the cloud container on `main` too, because Node 22 prints an `UNDICI-EHPA` experimental warning to stderr. CI runs Node 24 and passes.
