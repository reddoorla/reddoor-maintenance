# 2026-10-21 — time-travel syncs the cockpit, and can see a cockpit clock bomb

**Where it landed:** this PR (branch `claude/1616-time-travel-sync`), for #1616, found by the P1-33 next-5 sweep (`audits/2026-10-21-nightly-negative-controls/README.md` in reddoorla/reddoor-workspace). The two throwaway branches `claude/1616-time-travel-proof` and `claude/1616-time-travel-bomb` hold the Actions proof and are not meant to merge.

**Why.** `time-travel.yml` ran `pnpm test` with nothing before it but install and the browser. The cockpit tests load `cockpit/.svelte-kit/tsconfig.json`, which only `svelte-kit sync` writes. ci.yml and release.yml reach the sync only through `pnpm typecheck` → `cockpit:check`, so no PR check could notice its absence here. Reproduced on main at 77f266e8: `REDDOOR_TIME_TRAVEL_DAYS=90 pnpm vitest run cockpit/tests` gave `Failed to load tsconfig 'cockpit/.svelte-kit/tsconfig.json'` and `Test Files 35 failed (35)`. After `pnpm exec svelte-kit sync`: `35 passed (35)`, `576 passed (576)`. The next scheduled run (Mon 10-26, 4:00am PT) would have gone red and filed "Time-travel suite failing" with a wall-clock diagnosis for what was a load error, and until then the gate was blind to the cockpit's clock bugs, the class #1592 fixed by hand this morning.

**The fix** is a `pnpm exec svelte-kit sync` step from the repo root (svelte.config.js lives there and sets `outDir`), as its own step so a sync break files the outside-the-suite issue. The guard is a new block in `tests/ci-gate.test.ts`, beside the browser and `fetch-depth` guards: it parses every workflow as YAML and, in every job with a `pnpm test` or `pnpm test:coverage` line, requires an earlier root-level `pnpm exec svelte-kit sync`, `pnpm typecheck` or `pnpm cockpit:check`. It went red on `time-travel.yml:time-travel` before the fix and nowhere else.

**Mutations.** Each turned the guard red: removing the step; moving it after the suite; running it with `working-directory: cockpit`; and (added after review) a `run: |` block with the suite on its second line and no sync. The third is honest only as a guard rule: a sync from `cockpit/` finds no config, writes a default-config tsconfig whose `rootDirs` is `cockpit/` instead of the repo root, and the 35 files still load and pass today. The brief's wording ("the root instead of the cockpit") had the layout backwards; the root sync is the correct one.

**Proof on Actions, +90 days.** The first two runs on the fix branch, [39616151986](https://github.com/reddoorla/reddoor-maintenance/actions/runs/39616151986) (b5de933e) and [39616727377](https://github.com/reddoorla/reddoor-maintenance/actions/runs/39616727377) (388d0960), loaded every cockpit file and failed on exactly one test outside the cockpit: `tests/model-bakeoff/pnpm-update.test.ts` "reads an exit code of 0 beside a log …", `expected null to be 'log:failed'`, 1 failed | 634 passed. It is not a clock bomb. The test sets mtimes from the shifted `Date.now()` and then lets the filesystem stamp `check.exit` with the real clock, so the exit file reads 90 days older than the log. It passes 51/51 on the real clock and can never fail on main by itself. A fresh branch of another session (`claude/od137-seeded-one-defect`) touches that file, so it is filed as #1622 rather than fixed here. The known-good run therefore sits on `claude/1616-time-travel-proof`, the fix plus a one-line real-clock patch to that test: [39617716339](https://github.com/reddoorla/reddoor-maintenance/actions/runs/39617716339) green, 635 passed.
