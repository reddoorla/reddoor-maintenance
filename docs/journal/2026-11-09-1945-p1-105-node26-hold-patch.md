# 2026-11-09 — The org preset holds Node below 26 until AWS Lambda's nodejs26.x is GA (stored patch, branch `claude/p1-105-node26-hold`)

> Backlog: P1-105. Patch stored; done when the operator applies it to `reddoorla/.github` and Renovate closes the Node 26 PRs. Issue reddoorla/reddoor-maintenance#1976.

**Why.** P1-99 holds the fleet on Node 24 until AWS lists Lambda `nodejs26.x` as GA. Netlify runs server functions on the build's Node only when Lambda supports that major for production, and otherwise falls back to `nodejs24.x`. So a Node 26 build with `@types/node` 26 typechecks Node-26-only APIs that then throw in production (workspace `decisions/2026-11-04-1809-erp-node26-functions-stay-on-24.md`). The org preset had no rule about Node at all (`grep -i node` on both preset files printed nothing). So Renovate opened "update node.js to v26" PRs fleet-wide, and a red one puts its site in the cockpit's Watch.

**Verify-first contradicted the brief, and the session stopped.** The cockpit read 8 open PRs at 11:17am PT. At 11:33am PT the search returned 7. The eighth, reddoorla/medical-solutions-of-texas#114, had been merged into MSOT `staging` at 11:31am PT by the operator's account, with no note. At 11:35am PT AWS's runtimes page still called Node 26 "public preview … should not be used for production workloads". I wrote workspace `decisions/2026-11-09-1934-p1-105-msot-node26-merged-against-hold.md` and asked. Answer (a): the hold stands. Reverting MSOT `staging` to 24 is a separate task (queued as a card), and this rule does not do it, because Renovate never downgrades.

**What the patch does.** It adds one `renovate-config.json` rule: `matchDepNames: ["node", "@types/node"]`, `allowedVersions: "<26.0.0"`, and deliberately no `matchManagers`. Its `description` names the hold, both decision files and the lift condition. `validate.yml` gets a guard that asserts the hold leg by leg. The `.github` journal gets an entry. The diffs of reddoorla/the-pointe-burbank#62 (`.nvmrc` only) and reddoorla/29-navy#117 (`.nvmrc`, two workflows' setup-node `node-version`, `@types/node`) show the managers in play.

**Measured with Renovate 44.199.2, `--platform=local --dry-run=lookup`.** The fixture repo carried Node in every place the fleet might: `.nvmrc`, `.node-version`, `.tool-versions`, a `node:24` Dockerfile, `engines.node`, `@types/node` `^24.19.2` and a setup-node `node-version: "24"`. Every one was extracted as depName `node` (or `@types/node`).

**Beliefs corrected on contact.**

- I first capped at `<25`, believing `<26` would let Renovate propose `@types/node` 25 (25.9.9 is on npm) and Node 25. It does not. Renovate looks up `@types/node` with node versioning (`"versioning": "node"` in the debug log, from `workarounds:typesNodeVersioning`), and that versioning treats a non-LTS major as unstable. The patch uses the brief's `<26.0.0`.
- I also first named the `.nvmrc` manager `nvmrc`; Renovate calls it `nvm`.

**`deps-held.ts` needs no change.** `capsFromPreset` gives `[["typescript","<7.0.0"]]` for both the old and the patched preset. The new rule's exact-name `matchDepNames` keeps `excludes()` true for `typescript`, so `typescript` stays held. `node` is not an npm package the deps audit reads. `@types/node` is already held by the runtime-major rule (`:21-23`), so `HELD_CAP_PACKAGES` stays `["typescript"]`.
