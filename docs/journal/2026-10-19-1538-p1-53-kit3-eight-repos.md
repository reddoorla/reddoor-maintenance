All sixteen PRs were red, and neither PR in a pair can land alone. Per Operator decisions 113, each repo got one migration PR into a new `staging` branch (reddoor-website already had one), merged on green, with a promotion PR left for the operator. The sixteen Renovate PRs are closed as superseded. Every promotion PR names the `staging` ruleset command to run before its merge.

**Shapes, as the brief asked.**

- **Factory-shaped (`createSvelteConfig`):** caltex-landing, espada, la-homelessness-initiative, reddoor-website. These moved to 0.109.0's `createKitConfig`, the first release whose peer range admits kit 3.

**Netlify, and a refusal.** The runbook has the worker set `allowed_branches: [main, staging]`, and Operator decisions 113 says sessions do so with `NETLIFY_PAT`. Auto mode refused the PATCH as "Modify Shared Resources". Without it there is no staging URL, and, measured on 29-navy#82, no deploy preview for a PR into `staging` either: `deploy-preview-82--29-navy.netlify.app` answered 404. That PR was the first to show it. The operator answered yes through AskUserQuestion, and the seven sites were patched with a before/after diff of `build_settings`; only `allowed_branches` changed on each. LAHI's Netlify site is named `la-homelessness-general`, which a name search for the repo does not find.

**What the eight shared, past the plan's list.**

- `@reddoorla/maintenance` 0.104 and earlier declare peer kit `^2` only. pnpm installs regardless, so the starter-shaped repos stayed put.
- `ClientInit` and `Handle` live in `@sveltejs/kit/hooks`.
- svelte-check cannot resolve `$app/environment` at all, so every use moved to `$app/env`.
- Kit 3 writes its generated client under `.svelte-kit/generated/build/`. caltex-landing#82 went red in CI on this ("CI must build before the smoke suite") while passing locally, because the worktree still held the kit 2 file at the old path. A clean build has only the new one.
- 1836dig's and data-dynamiq's `scripts/privacy-services.ts` read `kit.csp` from `svelte.config.js`. Left alone, the privacy page would have dropped Netlify from its service list. Each repo's own "this site" spec caught it.
- caltex-landing pinned kit's `cookie` to `^0.7.0` as a security floor, and kit 3 asks for `^2.0.1`. Under the pin the build was green and the dev server failed every request ("stringifySetCookie not found"). The pin's own comment said to remove it once the parent range caught up, and it was removed.
- reddoor-website reads nine environment variables, not the starter's three. Copying the starter's `src/env.ts` would have silently broken the booking funnel, the prospect reports and staging's hidden-content switch. Its gate also fails on a computed-key read, which it caught on one real file.
- espada's root layout used `$app/stores`. On kit 3 that did not throw: `page.data` was undefined, so every page answered 500.

**Review rounds, and the one that would not converge.** Seven repos cleared in one or two rounds, with minors filed as issues. Beachfront took all five rounds, and each of the first four found a major of the same kind. With `paths.origin` deliberately unset, kit 3 prerenders with `http://sveltekit-prerender` as `page.url`'s origin, and only reads through `$lib/seo`'s `siteOrigin` get the production URL. In each round I fixed the instance the round had found, and the next round found another spelling:

- round 1: no test at all;
- round 2: the sitemap's `<loc>` built as `new URL(path, url).href`, which slipped past a call-site pin;
- round 3: the layout's JSON-LD built as `protocol//host`, which slipped past a source scan;
- round 4: an encoded `encodeURIComponent(page.url.href)` share, which slipped past the first output check because it matched only the literal `http://sveltekit-prerender`.

Each of these built green and would have shipped the placeholder into 80 pages or the whole sitemap. Round 3 is where the fix finally moved from the source to the output. `scripts/prerender-origin.mjs` builds with `URL` set, as Netlify does, and fails on any built file that names the bare host. Its control requires at least 50 files carrying the production URL: 195 built, 82 carrying it. Round 5 found nothing major. **Belief corrected:** a source scan for this hazard is a list of spellings, and three rounds proved the list never ends. The output is the only place the question has one answer. The other starter-shaped sites with prerendered origins (29-navy, vida, mantis, the starter itself) carry only the source-level tests today.

**A gap that held across five repos.** Espada's round 1 found that the starter-derived origin test never set `NETLIFY` or `CI`, so a `paths.origin` gated on `NETLIFY`, the starter's own idiom, passed every test. It was fixed on espada and filed on 1836dig, data-dynamiq, caltex-landing and reddoor-website; la-homelessness-initiative already had #55.

**Two accessibility-audit summaries changed and lost nothing.** On caltex-landing and espada the a11y step went from "0 violations across 2 routes (+1 hydration smoke)" to "1 of 2 routes (1 skipped: animate-in demo)". Neither site ever had `/dev/animate-in`. maintenance 0.90 and 0.95 counted that route's 404 page, which is the false green #680/#900 describe. 0.109 skips the missing fixture and downgrades the summary to `warn`, which drops the hydration note while the smoke still runs. The fix is a one-line `absentFixtures` declaration, filed as caltex-landing#83 and espada#89.

**Worker hygiene.** The six migrations ran as parallel subagents, each in its own repo worktree. Two of them kept mutation backups under the same shared `/tmp` names (`/tmp/l.bak`), and espada's "restored" layout came back holding caltex's icon import. Every pushed layout was then diffed against its pre-migration commit: each changed only its own `$app/stores` and `PrismicPreview` lines. The briefs should say "backups go in your own scratch dir", and the later review prompts did.
