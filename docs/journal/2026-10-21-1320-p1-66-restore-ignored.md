# 2026-10-21 — P1-66: `restore/` is git-ignored, and the runbook deletes the plaintext dump

**Where it landed:** this PR (reddoorla/reddoor-maintenance, branch `claude/p1-66-restore-ignored`), for #1558, backlog item P1-66.

**Why.** `docs/runbooks/continuity.md` section 6 downloads the nightly Turso backup into `restore/` at the repo root and decrypts it there to `restore/dump.sql`: the whole fleet database in plaintext, client leads included. Nothing ignored that directory, so in this public repository a `git add -A` in the checkout where someone had just run a restore would have staged the dump. Before the change, `git check-ignore restore/dump.sql` exited 1; after it, 0.

**What changed.** `.gitignore` gains `/restore/`, anchored to the root like `/reports/` and `/.lighthouseci/`. The runbook gains a step 7: once step 6 is green, `rm restore/dump.sql`, because the ignore keeps the file out of git and does nothing about it sitting on the disk. The encrypted `dump.sql.gpg` may stay.

**The test.** `tests/docs/restore-ignored.test.ts` asks git itself (`git check-ignore -v --no-index`) about `restore/dump.sql` and `restore/dump.sql.gpg`, and requires the matching rule to come from the repo's own `.gitignore`. That second half matters on the laptop: the machine-wide `~/.config/git/ignore` there already carries a `**/.claude/` rule (the `.gitignore` comment on Decision A9 says so), and a broad rule of that kind would make a bare exit-code check pass with the line deleted. A negative control (`restored/dump`, which no rule covers and whose missing extension no global `*.sql` can match) proves the check can answer "not ignored". The review caught that `git check-ignore -v` exits 0 for a `!` negation as well, printing the re-including rule, so `/restore/*` followed by `!/restore/dump.sql` passed the first version of the test while the dump was stageable again (a plain `git check-ignore` exits 1 for it). Appending only `!restore/dump.sql` after `/restore/` changes nothing, because git cannot re-include a file whose parent directory is excluded; the test now reads the pattern and counts a negation as not ignored.

**Mutations.** All four turned the test red, with the negative control still passing. The brief's two, deleting `/restore/` and changing it to `docs/restore/`, failed both cases. Two of mine: deleting the line while a scratch `core.excludesFile` holding `restore/` was in force (both cases failed), and turning the line into `/restore/*` followed by `!/restore/dump.sql` (the `dump.sql` case failed; it passed against the pre-review test). Before the fix the same file failed the same two cases, so it was red first.

**Checked and left alone.** The nightly `fleet-db-backup` job writes its plaintext dump to `$RUNNER_TEMP` (`.github/workflows/fleet-db-backup.yml`, the "Dump + rehearse the restore" step), outside the checkout, so only the hand-run restore had this exposure.
