# 2026-11-12 — P1-109: land-prs waits for the base's required checks

Landed in reddoorla/reddoor-maintenance as reddoorla/reddoor-maintenance#2040 (closes #2035). It changes `scripts/land-prs.mjs`, its types and its tests, and adds a changeset.

On 11-11, `land-prs 142 --repo reddoorla/vineyard-custom-homes --base staging` printed `checks passed on 9329069` and then stopped on `mergeStateStatus=BLOCKED`. The `staging` ruleset requires `ci / ci`, and that run was still queued with no check run; only Netlify's three runs existed. The watcher took "every run that exists has concluded" as passed, so a required check with no run yet was invisible. The stop line then blamed the wrong cause.

**The fix.** The base's required contexts now come from two places: the rulesets' `required_status_checks` rule (land-prs already read the rules for the merge method) and classic branch protection (`GET branches/<base>`). The wait passes only when each required context has a passing, neutral or skipped run or status on the head. A missing one is waited for under the checks timeout and named when it stops (`required check \`ci / ci\` has no run on 9329069 after 20 min`). A cancelled one stops the run. While the wait is held by required checks alone, each poll re-views the PR. A PR whose head moved on, or that is no longer open, goes back to the gate, and a wait that did not pass always re-gates. Live check: maintenance `main`requires`{"context": "build"}`, and its check run is named `build`. Its classic protection reads `enforcement_level: "off"`, so its own landings are unchanged.

**Beliefs corrected on contact.**

- The brief and the issue both pointed at `rules/branches` alone. Round 1 found, from two lenses independently, that private fleet repos have no rulesets: their rules read 403 "Upgrade to GitHub Pro", measured here on reddoor-workspace, which is private. The self-updating recipe requires `ci / ci` on them only through classic protection. Reading rulesets alone would have fixed vineyard (public) and left every private site with the same symptom. `GET branches/<base>` returns `protection` to the App on a private repo (reddoor-workspace answered, enforcement `off`). `branches/<base>/protection` answers 403.
- The first cut stopped at once on a cancelled required check. Round 2 showed that under `cancel-in-progress`, a push mid-wait cancels the old head's run, a case `main` handles by re-gating. My round-2 fix returned early on a moved head. Round 3 then reproduced two defects in that fix. First, a head that moved A→B→A merged A on a wait that never saw a pass. Second, a missing check on a head that had moved waited 20 minutes and named the stale SHA. The round-3 design (the wait returns pass or not, re-views while held by required checks, and any wait that did not pass re-gates) is what landed. Round 4's correctness lens traced every path to the merge and found none that skips a passing wait on the merged head.
