## 2026-10-07 — The PM pass reads the cockpit: `scripts/pm-cockpit.mts` (P1-35, #1244)

The weekday pass read the cockpit's attention and watch state only on Mondays, so a site signal that leaves every nightly green never reached a morning report. Data Dynamiq's Search Console `no-property` was the instance. `scripts/pm-cockpit.mts` now builds `buildCockpitModel` from the same eight Turso inputs `netlify/functions/fleet-homepage.mts` loads, and the pass runs it as a new step 2. The one deliberate difference from the page: any read failure is a hard error. The page degrades instead, and for the digest snapshot that would be the worst possible degradation, because with no snapshot nothing can be marked waiting and every "just wait" item reads as an ask. So the script also refuses an empty snapshot outright, at the cost of erroring on the one day the fleet is genuinely clean.

**Read-only is proved, not declared.** The connection is a Kysely whose plugin throws on any node but `SelectQueryNode`, and every run first sends an UPDATE (to a non-existent id) as a control, refusing to continue unless the plugin rejects it. Removing the plugin turns exactly that test red. The script never calls `openDb`, which runs migrations; a test opens a fresh file database and finds `sqlite_master` empty afterwards.

**First live run, 15:40Z:** `broken=0 watch=2 approval=2 sites=17`, with Data Dynamiq and LAHI on Watch for `no-property` and four pending October drafts. A direct SELECT of pending reports returned the same four, a check from a different authority than the one under test. Data Dynamiq's ask was recorded as Operator decisions 93 by another session the same afternoon.

**`--since` without new state.** The only first-seen times in the store are the digest snapshot's `firstFlaggedAt` days, so `NEW` is per day and inclusive: an item flagged on the since-day can repeat on a second morning, which beats missing it. Watch reasons, approvals and failed deploys have no first-seen time at all and print `(undated)`. The motivating `no-property` signal therefore can never be `NEW`; the docs say to read the Watch line daily rather than pretend otherwise.

**Review cost two rounds and an operator answer.** Round 1 found two real blockers. An exhausted vuln was dated by its first flag, when the moment it became an ask was exhaustion. And the cockpit's own Needs-you feed drops `model.cardless`, which today is precisely the "leads are being dropped for an unknown slug" dead-letter alarm. That gap also exists on the live page's feed (the page shows it in a separate lane); a failed-deploy-only red card is likewise absent from the page's feed, and the script now lists both. Round 2 found the docs contradicting the code: a vuln past its wait but not exhausted is a self-patching vuln, so the feed puts it in **Watch**, yet the step said Watch is never `NEW` and only Needs-you reaches the top of stack. Per the two-round rule that went to Operator decisions 94 (#1245); the operator answered (a), fix and land without a third round. The fix was the wording, the "undated broken" rule excluding `… ready` approvals, and the cockpit's own ordering for entries the script adds.

**Corrected on contact:** I expected exhaustion to be the common "dated today" case. The digest writes the snapshot at about 09:23Z, before the morning pass, so by the time the pass runs the exhaustion is usually already recorded and the vuln prints `(undated)`. It still reaches the top of stack through the undated-broken rule.

**Self-inflicted, now undone:** `git checkout -B <branch>` inside the new worktree moved the branch ref that the main checkout had checked out, leaving the main checkout's HEAD ahead of its files. I detached the main checkout at its old commit before anything was committed from it.
