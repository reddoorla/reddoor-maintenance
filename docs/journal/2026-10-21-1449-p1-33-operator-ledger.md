**Why.** Every judgement about the loop rested on feel. Nothing counted asks answered, release waits, reverts or fix-of-fix PRs (the two-touch review, "next" 8). The decision files from the 10-20 cutover made the ask half countable.

**What it does.** `node scripts/operator-ledger.mjs <home base> --week <Monday>` prints six lines for the seven PT days before that Monday:

- open asks at the week's end, with the oldest one's age and a stale count;
- asks answered, with median and p90 repository latency;
- asks born, by kind;
- release-PR waits;
- fix-of-fix PRs and reverts.

It stores nothing. The asks come from the home base's git history on `origin/main`, not its working tree, so an ask that exists only on a branch is never counted. A week is judged only by commits before its end, so it reads the same however often it is re-run. The PR lines come from REST, paged by hand.

**Beliefs corrected on contact.** `git log --follow` and copy detection cannot follow a decision file. Every ask starts from the same template, so git reads a new ask as a 63–67% copy of an older one and grafts their histories together. The script reads one directory log with renames only, and accepts a rename only between names with the same `YYYY-MM-DD-HHMM-` prefix.

The workspace clone the session started with was shallow (50 commits), which would have dated asks wrongly. The script now refuses a shallow clone.
