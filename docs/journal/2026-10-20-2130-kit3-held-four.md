## 2026-10-20 — SvelteKit 3 and adapter-netlify 7 on the four repos P1-53 held back, and the launch pre-flight that kit 3 broke

Landed in the PR that carries this file, which also fixes `reddoor-maint launch`'s `/dev/match` guard check. The site PRs: reddoorla/vineyard-custom-homes#96 (`3321046`), reddoorla/erp-industrial#79 (`dea7f9a`), reddoorla/williamson-homes#47 (`630d30e`) and reddoorla/williamson-construction-co#37 (`5455b0a`). Decision: the home base's `decisions/2026-10-20-1924-evening-queue-four.md` (a); brief `briefs/2026-10-20-kit3-held-four.md`.

P1-53 (`2026-10-19-1538-p1-53-kit3-eight-repos.md`) moved eight repos and held these four behind P1-64's `@types/node` fix. Each repo's two Renovate PRs, kit 3 and adapter 7, were red alone and could only land together, so each repo got one PR replacing both. Unlike P1-53's eight, none of the four has a `staging` branch or runs `main-gate`, so each landed straight on `main`.

**Two shapes, two recipes.**

- **vineyard and erp are factory-shaped.** They swapped `createSvelteConfig` for `createKitConfig` exactly as caltex-landing did, and took caltex's Playwright gate (`tests/kit-config.spec.ts`).
- **The two williamson repos are starter-shaped,** and most of their files were still the starter's. williamson-homes had 22 of the 39 files #187 touched there byte-identical to the starter's pre-migration versions. So reddoor-starter#187 and #188 went on as a patch.
  - Each site's own CSP was then carried onto the new `sveltekit.config.js`, and the old and new configs were loaded side by side and compared as objects. CSP, handlers, `compilerOptions` and `preprocess` came out equal; the only addition is the `$lib` alias.
  - The patch's rejects and everything the starter does not have were done by hand. A sweep for every kit 2 spelling found what the build did not:
    - construction-co's `join-the-team` form read `$env/dynamic/private`, which kit 3 leaves `undefined` without `src/env.ts`;
    - two `csp-policy.test.ts` cases read `config.kit?.csp`, which on kit 3 checks an empty list;
    - the privacy-services fixtures were still kit 2-shaped, so they tested an empty config;
    - `ClientInit` must now come from `@sveltejs/kit/hooks`;
    - vitest's strict mocks failed 9 intake-form tests once a namespace import of `$app/env/public` needed the export to exist.

**erp's canonical origin.** It was the one thing none of P1-53's factory-shaped repos had. erp built `<link rel="canonical">` from `$page.url.origin` and relied on `prerender.origin = URL`, which kit 3 removed. It now uses the starter's route: `productionOrigin`, a `define`, and a minimal `$lib/seo.ts` holding only `siteOrigin`. Beachfront's `scripts/prerender-origin.mjs` runs first in `pnpm test`. Its control is measured on erp's own kit 2 build (33 files, 10 naming production), not Beachfront's. The kit 3 build gives 32 and 10, and its 8 canonical links are byte-identical to `main`'s.

**Review: what the gates missed, by repo.** Every PR ran three lenses: runtime, completeness, and gate and evidence integrity. The runtime lenses never found a visitor-visible difference. They built `main` and the branch side by side and diffed the prerendered output, every absolute URL, the CSP on prerendered and SSR pages, and the forms against a stub ingest, including CSRF on several hosts. The gate lens found a major on every repo:

- **vineyard, erp and williamson-homes: a `paths.origin` guarded on `NETLIFY` or `CONTEXT` passed the origin test.** The test set `URL` and the deploy URLs but not the variables a config actually branches on. This is the gap P1-53 filed against five repos ("never set `NETLIFY` or `CI`"), still open in the starter's own gate. Each gate now sets Netlify's whole build environment and runs once per deploy context.
- **williamson-homes: nothing checked the built output.** A JSON-LD `url: page.url.origin` in the layout shipped `http://sveltekit-prerender` into all 10 pages, and every test stayed green. `prerender-origin.mjs` went into both williamson repos with each site's real origin. The first williamson-homes comparison had been built with a wrong one: my grep cut `williamson-homes.netlify.app` to `williamson-homes.net`, a domain that does not exist. The live sites' canonicals give `www.williamson-homes.com` and `www.williamson-construction.com`.
- **construction-co: the launch pre-flight, fixed in this PR.** `carriesGuard` required the string `$app/environment`. On kit 3, svelte-check cannot resolve that name, so the migrations import `dev` from `$app/env`. The guard was still in place, yet `reddoor-maint launch` would have stopped both williamson sites at step 0 with a false "the matching twin would ship".
  - The check now accepts either module, quoted, so `$app/env/private` does not count.
  - A test proves each direction.
  - Its own review (one reviewer, all lenses) found nits only. One nit was a real contradiction: this repo's plan doc called `$app/environment` on kit 3 "a dev warning … not a break", and P1-53's journal said svelte-check cannot resolve it. Measured on williamson-homes at kit 3.1.0: `pnpm check` fails with "Cannot find module '$app/environment'". The plan doc's row now says so.
  - The match-harness template still writes `$app/environment`; that is #1566.

Round 2 on vineyard, erp and williamson-homes found minors only, so those rounds were clean. construction-co's round 1 was clean on its own diff: its one major was the launch check above, fixed here. Minors in files a PR already touched were folded in. The rest are filed:

**Beliefs corrected on contact.**

- **"An undeclared env read is silent except at runtime" was overstated twice.** First it was "only a build warning". Then it was "svelte-check is silent on `.js`". Both were wrong: with `checkJs` on, svelte-check fails on an undeclared read in every checked file. The gate holds the line when `pnpm check` is skipped.
- **caltex's tsconfig `include: ["src", "tests", "*"]` is not neutral.** On erp it newly type-checked `tailwind.config.js` and gave one error that kit 2 never reported. erp's include now matches kit 2's coverage.
- **Removing a lockfile floor changes nothing when the floor no longer matches.** vineyard's and erp's `cookie@<0.7.0` floors only match versions below 0.7, so removing them changed no resolved version. They went because their stated reason ("kit still declares `cookie ^0.6`") was false.
