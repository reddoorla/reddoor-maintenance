# 2026-10-21 — fleet-config-drift: a shrinking roster and a lost filing; a disabled Renovate job split out

**Where it landed:** branch `claude/1607-config-drift-blind`, for #1607 parts 1 and 3. Part 2 (a disabled Renovate job) was split out after six review rounds and stays open on #1607. Brief: the workspace's `briefs/2026-10-21-last-three-blind-gates.md`, from the P1-33 next-5 sweep (#1595).

**Why.** The sweep found three ways the weekly drift run read a bad week as green.

1. **The roster.** `selectFleetSites` visits only rows whose Status is in the vocabulary. With 3 of 4 rows on the retired `maintenance` (the restored-backup case `site-status.ts` names), the drifted repo among them, the run printed `drifted=0 clean=1 skipped=0 total=1` and passed.
2. **The Renovate job.** `renovateActionGaps` checks strings, so `if: false` on the job, with pins, auth and cron intact, read `CLEAN`.
3. **The filing.** `gh issue create` returning 502 under `continue-on-error` left the job green, and the drift appeared nowhere for a week.

**What changed.**

1. **The roster.** The selection rule itself is untouched: every fleet sweep shares it, and it is right not to visit a row whose Status it can't read. Instead `fromTursoDb` hands the dropped rows (`rowsWithUnrecognizedStatus`) to a callback, and `sync-configs` reports each as `SKIPPED <repo> status "maintenance" is not in the vocabulary…`. They now count toward `total`, keep a drift issue open, and past half the roster red the run through the gate that already existed.
2. **The Renovate job: not in this PR.** See the last two paragraphs.
3. **The filing.** A last step reds the run, naming the drift, when the open step failed. It sits after the outage pair, so it files no false "sweep failing" issue. The open step fails when this week's drift reached no issue: the create failed, or on an open issue both the rewrite and the comment failed. One failed write of the two is a warning.

**Known-good.** The 2026-10-18 run printed `drifted=15 clean=0 skipped=0 total=15`. I fetched those 15 repos' `renovate.yml` read-only (a sparse, shallow git clone of the one file). All 15 had 0 gaps under the split-out `if:` check and carry no `if:` at all, which the #1607 follow-up can reuse as its known-good set. Whether any production row sits on an unrecognized Status today needs a production read, which this session's permissions refused; the cockpit already shows such a row as a watch item.

**Belief corrected on contact: a line regex is not a YAML reader.** My first push matched `if:` lines with a regex. Review round 1 showed it would have called `if:` followed by `github.repository_owner == 'reddoorla'` on the next line (one plain scalar continued) constant-false, because the regex saw an empty value. Any gap makes `sync-configs` heal the file by overwriting it, and makes self-updating open a PR, so the site's real guard would have been deleted. The same regex matched `if: false` inside a `run: |` body, and missed `if: >-` over `false`. No YAML parser is a runtime dependency of the package (`js-yaml` is dev-only), and adding one to fix a check is not this PR's call. My second version, a one-pass scanner guessing structure from the nearest shallower line, failed round 2 the same way. It flagged a site's own `sidecar:` job with `if: false`, an `if` key inside a required step's `env:` map, and `${{ 'false' }}`. I believed then that this was a non-empty string, so truthy; round 5, using GitHub's parser, showed the parser unwraps it to `false` and the job is skipped. Not reading it is a safe miss either way. Each would have overwritten a file over a job that runs. The third version is built the other way round: it anchors on the `renovatebot/github-action` step, and reads only `if:` keys at the exact column of that job's own keys, or of a required step's own keys in that job. Block bodies, nested maps, other jobs and a site's own steps all sit at other columns or outside those ranges, so none can match. What it cannot read, such as a quoted `"if":` key or a flow mapping, is a miss. A miss leaves today's blind spot; a false gap deletes a site's code. Of the two, only the miss is acceptable here. Round 3 found one more false gap: a site's own second checkout with `if: false` beside the working one was flagged. That is when the question changed from "is a required step disabled" to "can Renovate run at all". Now a gap needs every renovatebot step to be blocked, by its job's `if:`, its own, or every copy of another required step. Round 3 also caught a stray `tpl.yml`: a reviewer's scratch file that my `git add -A` committed. It is removed.

Round 4 corrected two beliefs of mine against GitHub's own workflow parser (`@actions/workflow-parser`, `convertToIfCondition`). First, an empty or null `if:` does not disable a job: "Empty condition defaults to success()", so the job runs. I had been flagging `if: ''` and `if: null` as disabling, so those were false gaps too. Second, a disabled checkout does not stop Renovate: the action works through the API, and the template passes it no config file. The App token is the only other step whose output Renovate needs. The same round found the filing gap's twin: on an issue that is already open, both the rewrite and the comment can fail, and the run stayed green.

**Tests.** The roster case runs the real `--fleet turso` path on a migrated `file:` database with pre-made checkouts. Mutations on what landed: the callback discarding the rows, the predicate never matching, dropping its `url` guard, dropping the last step, a missed comment redding the step, and both writes failing staying green each turn a test red.

**Stopped at the review-round limit.** Round 5 reproduced one more false gap. To Actions, `"${{ false }} "` (whitespace inside the quotes) and a `|` block holding `${{ false }}` are both truthy `format()` strings, so the job runs, but the check flagged them. The fix is on the branch, unreviewed: padded quoting and block expressions are now misses. Five dirty rounds means no sixth, so the PR waits on the operator's decision (`decisions/` in the home base). Parts (a) and (b) have been clean since round 3. Every round from 1 to 5 found a false gap in (c).

**Split out after round 6.** The operator chose a sixth round, falling back to a split if it found another false gap (`decisions/2026-10-22-0016-config-drift-1607-round-5.md`). Round 6 confirmed the round-5 fix against GitHub's parser: 210 cases, no false gap. Then it found two new ones. An `if: false` continued by `|| true` on the next line was cut to its first line. A quoted `'false'` inside a `|` block was unquoted, though Actions reads it as a non-empty string and runs the job. Six rounds, six new false gaps, every one in YAML forms a column reader had not met. So `renovate-action.ts` and its tests are back at main's version, and part 2 returns to #1607. The note there says to build it on a real YAML parser and to use `@actions/workflow-parser`'s `convertToIfCondition` as the oracle. The rounds' inputs make a ready test matrix. What landed is parts 1 and 3, which were clean from round 3 on.
