# 2026-10-21 — A Renovate drought gets its own tracking issue (#1606)

**Where it landed:** this PR (reddoorla/reddoor-maintenance#1633, branch `claude/1606-renovate-drought-alarm`). It changes `fleet-security.yml` (three new steps), `protection-audit` (a `DELIVER` line, and a failed probe now counts as unmeasured), and adds `tests/build/renovate-drought-issue.test.ts`.

**Why.** Since S7 the protection audit has measured when a feature-update Renovate PR last landed on each repo. It prints that measure on its own `RENOVATE_OUTCOME` prefix, on purpose, so that a drought never holds the posture issue. Nothing read the line. The 2026-10-21 negative-control sweep fed it the 09-14 freeze shape and got `drought=4 delivering=0` beside `PROTECTION_AUDIT gaps=0`, exit 0. The alarm existed; its delivery did not.

**Known-good first, and it was a finding.** Last night's real run (39554147850) printed `RENOVATE_OUTCOME drought=21 delivering=5 unmeasured=4 threshold=21d`. Fed through the new steps, it files "Renovate drought: reddoor-starter, erp-industrial, … (+11 more)". Seventeen repos are at 28 days, all last fed by `renovate/pnpm-12.x` on 09-22. erp-industrial is at 69 days and 29-navy at 22. I checked from a second authority, git history instead of the PR API. Since 09-22, espada's `main` has merged only `[security]` and lock-file Renovate PRs, and it has no `renovate/all-minor-patch` branch at all, while its deps audit counts 19 outdated installs. The grouped channel looks stopped again, four Monday windows running. So the alarm should fire on its first night on main, and correctly. The cause is not this PR's to diagnose.

**The operator's call: only a drought opens the issue.** The brief said an UNMEASURED outcome should open it too. Review round 2 fed that rule the fleet's own known-good snapshot, the 2026-08-10 PASS control pinned in `tests/audits/renovate-outcome.test.ts`. That snapshot reads `drought=0 delivering=20 unmeasured=6`. The alarm opened on it, and it could never have closed, because two repos have never merged a feature update and two merge too many PRs for the 100-PR window. So on a healthy fleet the issue would sit open for good, and a real freeze would arrive only as a retitle. It went to the operator as `decisions/2026-10-21-1513-renovate-drought-unmeasured.md` in the workspace. The answer, at about 8:40am PT, was (a): a drought opens and holds the issue, and UNMEASURED repos are listed in the body and neither open nor hold it. A repo the issue names still has to print `DELIVER` before the issue closes, so "unmeasured" never reads as "fixed" for a repo already known to be dry. The 08-10 line now reads `drought=no`, and a test pins that.

**Defects found in review, named.**

- **Round 1 (major).** A public repo whose posture probe threw (a 502 on its dependency dashboard) carried no Renovate outcome at all. The fleet line read `unmeasured=0`, and the issue could close without that repo ever being looked at. The CLI now counts such a row as unmeasured. The fix is in `protection-audit.ts`, not `protection-coverage.ts`, because `src/audits/**` belonged to another session today. Under the operator's rule, that row no longer opens anything, but it still holds an issue that named it.
- **Round 1, tests.** Seven mutations survived the first suite. The two that mattered most were a loosened `if:` (`!= 'no'` would have filed an unclosable issue on every skipped audit) and a prefix repo match (`espada-cms` vouching for `espada`). The shared tracking-issue evaluator gives every step output one value, so it cannot tell `== 'yes'` from `!= 'no'`. This file now evaluates the real `if:` itself.
- **Round 2 (major).** The known-good snapshot opened the alarm, as above.

**Belief corrected.** I first read "UNMEASURED opens the issue" as the conservative choice, because "I could not measure this" must not read as "fine". On the fleet's own healthy data it is the opposite: an alarm that is always on reports nothing. Keeping unmeasured out of the open decision, while still refusing to count it as delivering, keeps both halves of the rule.

**Mutations.** The brief's four, the review's eight and five more for the decision were each applied in place and turned at least one test red. The PR body has the table.
