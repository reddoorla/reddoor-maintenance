## 2026-10-12 — SvelteKit 3: the starter migrated, `sync-configs` taught kit 3, and `paths.origin` left unset (reddoor-starter#187 `4e1f3b6`, #1301)

P1-45. Renovate opened `@sveltejs/kit` 3 and `@sveltejs/adapter-netlify` 7 in six repos overnight and all twelve PRs went red on `config_file_unsupported`: kit 3 refuses to start beside a `svelte.config.js`. This session took over from a worker stopped at ~14:00Z, with reddoor-starter#187 red and an unfinished WIP commit here.

**The red CI the handoff left was the test, not the build.** `scripts/prismic-barrel.test.ts` looked for `.svelte-kit/generated/client-optimized/app.js`; kit 3 writes it under `.svelte-kit/generated/build/`. Measured after `pnpm build` (both `build/client/app.js` and `build/client-optimized/app.js` exist; the old directory does not), reproduced as 3 of 8 red, then 8 of 8 with the path moved. The manifest under `.svelte-kit/output/client/.vite/` did not move, which is why only half the "built" check failed.

**Adapter 7 requires kit 3** (`peerDependencies`), so each repo's two Renovate PRs can only land as one change. Kit 3's peers are svelte ^5.57.1, vite ^8.0.12, vite-plugin-svelte ^7, typescript ^6 and node >=22.17: no Svelte 6, no Vite major, so the brief's stop condition did not apply. All six red repos are on vite 8, typescript 6 and Node 24; alamo-anatomy's lockfile has svelte 5.57.0, one patch under the peer.

**The defect review found, and the belief it corrected.** The previous worker had set kit 3's `paths.origin` from Netlify's `URL` and listed the deploy, preview and `*.netlify.app` origins in `csrf.trustedOrigins`, believing those were every host a build is served on. A correctness reviewer built with `URL=https://example.com`, drove `Server.respond` with same-origin POSTs to `/contact`, and got 502 (past CSRF, to the dead ingest URL) on the listed hosts and **403** on `https://www.example.org`. That is a Netlify domain alias, and it is also go-live: a custom domain attached after the last build keeps the old `paths.origin` until a redeploy, so every lead is refused. Kit 3 has no prerender-only origin (`paths.origin` feeds both prerender and `get_self_origin` in `runtime/server/respond.js`). The fix leaves `paths.origin` unset, so kit keeps kit 2's per-host CSRF check and its `http://sveltekit-prerender` placeholder, and puts Netlify's `URL` in place of the placeholder in `$lib/seo` (`siteOrigin`, fed by a Vite `define`). The same probe after the fix: production host, mirror and alias all 502, `Origin: https://evil.test` still 403, per-request canonical the asking host. Round 2 confirmed it independently and found one test gap (og:image), closed.

**I pushed a red commit once.** `e3ee0ea` went to #187 with `capability-index.test.ts` failing (a generated `docs/COMPONENTS.md` needed regenerating) because the command chained `grep` on the vitest summary into `git commit` with `&&`, and `grep` succeeds on a "1 failed" line. `718db58` fixed it, and every later commit in this session was gated on vitest's own exit code. **This repo.** `createKitConfig` is `createSvelteConfig` flattened for `sveltekit(...)`, plus `$lib`. The handed-off version did not typecheck: `Omit<SvelteConfigLike, "kit">` collapses an index-signature type, so `compilerOptions` lost its type. `sync-configs` now reads the declared kit major and on kit 3 never writes `svelte.config.js`; its `eslint` template is the starter's file byte for byte, held there by a fixture copied from the starter (`718db58`) and, when `REDDOOR_STARTER_DIR` is set, by a live comparison. What a sync cannot fix (a leftover `svelte.config.js`, an `eslint.config.js` still importing it, a kit spec it cannot read) is a DRIFT line whose third field says "move by hand", so the weekly issue does not tell anyone to heal it with a sync. `analytics-tag` refuses kit 3, after its already-installed check: it edits only `svelte.config.js`, and on kit 3 it would have said "no csp option" and installed a tag the real policy blocks.
