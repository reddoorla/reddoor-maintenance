# 2026-11-23 — P1-122: the cockpit moves to dashboard.reddoorla.com (held for DNS and Google)

Lands in reddoorla/reddoor-maintenance#2240, held unmerged. The tracking issue is reddoorla/reddoor-maintenance#2238. The operator asked Mon 11-23 about 9:30am PT for the cockpit to live at `dashboard.reddoorla.com` instead of `reddoor-maintenance.netlify.app`.

**Why it is held.** Netlify production sets no `DASHBOARD_BASE_URL`. I read the site's variable list through the Netlify API on 11-23, and it has twenty variables, none of them that one. So production runs on the code default, and merging this PR is itself the switch: from that deploy on, Google sign-in sends people to `https://dashboard.reddoorla.com/auth/callback`. Until the CNAME exists, Netlify has issued a certificate and that URI is registered on the OAuth client, merging locks everyone out. The shared password is refused on production whenever Google is configured. `reddoorla.com` DNS is still at Hover, and it moves to Cloudflare in Tuesday's R2 go-live.

**The risk the brief named, measured rather than assumed.** The brief's worry was that a primary custom domain would make Netlify 301 the netlify.app host. A 301 would turn the fleet's form POSTs and Resend's webhook POSTs into GETs. Netlify's docs say nothing about netlify.app either way. The only automatic redirect they describe is between apex and `www`. So I measured it on four fleet sites that already have a primary custom domain: `reddoorla`, `reddoor-staging`, `facing-cancer` and `gallerysonder`. Their netlify.app hosts answered GET and POST directly, with 200, 404 or 405 and no redirect. facing-cancer's 308 went to `/hi` on its own host, which is that app's route. The probe proved itself first: it reported the 301 from `http://github.com/` and the 308 from `http://reddoor-maintenance.netlify.app/…`. The control, taken before any change, was form ingest 401 and the Resend webhook 400 with no redirect, from unauthenticated, unsigned bodies that write nothing. So the plan is a primary domain, with the old host left live for the fleet's `FORMS_INGEST_URL`s and the Resend registration, and no fleet sweep.

**A defect the brief did not name.** The OAuth state cookie is host-only and is set on the host the flow starts on. Google returns to the canonical host's callback. A sign-in started on the old host, which is where the team's 11-20 link points, would therefore always end in `error=state`. `/auth/login` now hops to the canonical host first. Review shaped that hop over three rounds:

- **Round 1:** one major and five minors. The major was that the cutover order was written nowhere. The spec now gives it: domain and certificate, then the Google URI, then the base URL. Of the minors, a malformed base URL turned the login page into a 502, and the hop only worked in one direction.
- **Round 2:** one major. Nobody had measured which host Netlify puts in the Host header for a request on the custom domain, and a wrong guess would loop the canonical host onto itself. The hop now fires only when the Host header and `req.url` agree on one of the cockpit's two hosts, so no platform behaviour can make it loop.
- **Round 3:** minors only, so the round counted as clean. Two were folded in. The other two, absolute alert links and the WebFetch allowlist, went to reddoorla/reddoor-maintenance#2242.

**Mutations.** These turned tests red: reverting the code default (3 tests), reverting the hop tests' env (2), removing the hop (5), reading the host from `req.url` alone (1), removing the safe parse (1), removing the Host/url agreement (1) and removing the port strip (1). Setting the brief's literal outer `DASHBOARD_BASE_URL=<old host>` turned nothing red, because every test sets or clears the variable itself. That is correct test hygiene, and it is reported as is.

**Belief corrected on contact.** The brief said to set `DASHBOARD_BASE_URL` on Netlify after the operator's steps, as if the code default were inert. Production has never had the variable, so the default was always the live value. I could not read the repo's Actions variable of the same name: the proxy refuses `actions/variables`.
