# 2026-11-11 — P1-108: the browser audit's three retry-test gaps

Landed in reddoorla/reddoor-maintenance as the P1-108 PR (closes #2031, #2017, #2018). Tests and CI setup only; no `src/` change.

The review of #2014 (P1-107) left three holes in the evidence for the browser audit's retries. First, the mobile sidecar's m7 and m8 had stopped running at all. Second, nothing pinned most of the desktop page facts. Third, the desktop retry had never met a real Firefox, though Firefox is where the 11-10 false Broken came from.

**m7 and m8.** Verified first at `4693e6fd`: `mutate.mjs --check` refused both with `find matches 2 times in src/audits/browser.ts`, because `probeDesktopOnce` copied `probeMobileOnce`'s `gotoTimeoutMs: number = PAGE_TIMEOUT_MS,` line. The find now carries the `{ device, descriptor }: MobileTarget,` line above it. All 8 mutants run, and all 8 go red; m7 and m8 are each killed by the hang-twice timing test.

**The seven desktop facts.** One fixture page carries a value for each fact that no default can supply: status 203, a title, a meta description, two same-origin links plus one off-site, a `%sveltekit.body%` in a comment, `lang="fr"`, and an hreflang alternate. It runs through `probeRoutes` in production engine order and is checked with `toEqual` on the whole route. Each of the seven drop-one mutants goes red. Before this, four of the seven (meta description, links, leaked tokens, alternates) were killed by nothing. Status, title and lang were already pinned by P1-107b's "page facts come from its retried load" test, which landed after #2017 was filed.

**Real Firefox and WebKit.** I corrected a belief on contact: the obvious fixture, a connection reset before any reply (the `/drop-once` the Chromium tests use), never reaches our retry on Firefox. Firefox resends the request itself. One drop read 200 after 2 requests, and two drops read 200 after 3, with no throw. Chromium (`ERR_EMPTY_RESPONSE`) and WebKit ("Connection terminated unexpectedly") throw on one. Three other ways to break the first load were tried. A bare status line and a garbage response loaded as 200 on Chromium and Firefox. A response cut mid-body throws on Firefox (`NS_ERROR_NET_PARTIAL_TRANSFER`) and WebKit after exactly one request, so that is the fixture. Each test asserts two requests, two contexts and timeouts `[30000, 10000]`, so only the probe's own retry can pass it. The engines tested were Playwright's firefox-1572 and webkit-2388, installed by the setup hook at this `main` (the brief named 1555 and 2370; the lock file moved).

To run where the merge is decided, CI now installs Firefox and WebKit as well as Chromium, in ci.yml, release.yml and time-travel.yml. Review round 1 caught the one I missed: time-travel.yml runs `pnpm test` with Chromium alone, and the weekly run would have gone red with the old #775 symptom. The existing ci-gate check could not see it, because it only asked for some `playwright install`. A new ci-gate test requires each engine on the install line of every workflow that runs the suite. It went red on time-travel.yml (`firefox`, `webkit`) before the fix and green after.

Round 1 also found that the first Firefox mutant keyed on the engine label, so the older Chromium tests labelled "firefox" killed it whatever the new test did. e1 and e2 now key on `browser.browserType().name()`. After that, each one is killed by its real-engine test alone (1 of 137 failing). e3 drops webkit from ci.yml's install, and the ci-gate test goes red.

Review: round 1 was dirty (one blocker, one minor folded in, one nit). Round 2 was minors only, so it is clean. Its two findings were filed as reddoorla/reddoor-maintenance#2036 (the gate reads the whole file, not the job that runs the suite) and reddoorla/reddoor-maintenance#2037 (the regex misreads a bare or multi-line install and `test:smoke`). No workflow is affected today.

Watch the first CI run's install time: WebKit's `--with-deps` adds apt packages under ci.yml's 300 s per-attempt timeout.
