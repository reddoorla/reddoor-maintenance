**#1396 and #1471 (#1993).** I measured the DevTools pipe here (Playwright 1.64.1): a 100 MB `evaluate` string crossed it, and a 120 MB one closed the page. A full 128 MiB batch is 179 M base64 characters, so any batch over about 75 MiB failed. Files now reach Chromium by path, through a hidden input of the script's own and `setInputFiles`.

For the early stop, #1471 asked for a measurement of what the page retries. All eight file requests are closed, and creating one writes to the operator's Dropbox. A closed request's page still loads the submission bundle, though (`submission_edison-vfl7ETbh6.js`), and it settles most of the question:
- the commit is one XHR that resolves on any 200, whatever the body;
- a 403 disables the form;
- block uploads get three tries, and the commit gets none.

So any 200 and a 403 now end the wait; 5xx answers are still waited on. The scheduler that calls the commit is in a chunk that only an open request loads, so whether it retries a whole batch remains unread. The runbook says so.

A routed stand-in page now drives the real `uploadBatch` in Chromium, so the wiring that #1471 (2) said "needs Chromium" has a test. Two mutants were stillborn on the first run: the test's deadline equalled its timeout. Round 1 found a major of my own making: a soft reset left the runbook out of the commit. Round 2 found minors only. Filed: #1994, where a later commit answer overwrites an earlier `complete`.
