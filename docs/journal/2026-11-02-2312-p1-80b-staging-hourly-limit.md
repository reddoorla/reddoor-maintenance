## 2026-11-02 — P1-80b: the staging flow's hourly PR limit, a patch for `reddoorla/.github`

Landed in the PR that carries this file, as `docs/patches/2026-11-02-github-renovate-staging-hourly-limit.patch`, for the operator to open on `reddoorla/.github`. Brief: reddoor-workspace `briefs/2026-11-02-p1-80b-rate-limited-staging-prs.md`. Decision: reddoor-workspace `decisions/2026-11-02-1828-p1-80-staging-majors-rate-limited.md`, answer (c).

**Why.** Monday 11-02's in-window Renovate runs on revogen and medical-solutions-of-texas each opened two PRs, both into `main`, and left all five `staging` branches Rate-Limited: lock-file maintenance, the actions/setup-node digest, Node 26, @prismicio/svelte 3 and svelte-select 6. Branches without a PR can be created only in the one in-window run a week, so the default `prHourlyLimit` of 2 works out to two PRs a week, and the `main` groups take both.

**Belief corrected: `prPriority` puts lock-file maintenance first.** It does on a repo with one base branch, where it was proven (reddoor-starter#208). On the staging flow it does not. Read from Renovate 44.199.2, the version that ran: `sortBranches` runs at the end of `lookup()` (lib/workers/repository/process/extract-update.ts:363), once per base branch, and process/index.ts concatenates the results in `baseBranchPatterns` order. Nothing re-sorts the combined list before `writeUpdates` walks it. Every `main` branch is processed before every `staging` branch, whatever its priority.

**The change** sets `prHourlyLimit: 0` in `renovate-staging-flow.json`, so it reaches only the repos that extend that preset. On 11-02 those were fifteen, read from each repo's `renovate.json` on `main` and `staging` (raw.githubusercontent, every `reddoorla/*` name in this repo and the workspace): 1836dig, 29-navy, alamo-anatomy, beachfront-dentistry, caltex-landing, data-dynamiq, espada, gallerysonder, la-homelessness-initiative, la-homelessness-youth, mantis-landscaping, medical-solutions-of-texas, revogen, roalson-interests and vida-legacy-foundation. All fifteen carry the same two-line `extends` with no limit of their own.

For each of them the change is the same. The Monday run opens the `staging` branches in the same run as the `main` groups, up to `branchConcurrentLimit` and `prConcurrentLimit` (10 per repo, counted over both bases). Whether a PR may merge does not change. The actions/setup-node digest is the one branch that still does not open: the hourly check comes before the stability check (update/branch/index.ts:192, then :358), and a digest has no release timestamp, so it goes from rate-limited to pending. The first in-window run after the patch lands opens the waiting backlog at once.

**Proof.** Renovate's own `isLimitReached('Branches')`, called from the installed renovate@44.199.2 with the hour's count at 2, returned `true` with a limit of 2 and `false` with 0. With 10 branches already open it returned `true` again. `renovate-config-validator --strict` 44.199.2 passed both patched files and refused a copy carrying `nonsenseOption`. `validate.yml` gains three refusals, and seven mutations each turned its step red: the key removed, set to 2, to `"0"` and to `null`; a staging-flow packageRule with 2 and one with 0; and a renovate-config packageRule with 2. The patched presets passed, and `main`'s at `1a6e3b7` failed. The null and packageRule-0 cases are harmless to Renovate and are refused anyway, so the rule stays one readable key. This was not proven on a live run: the first in-window Monday after it lands is the check.

**Rejected:**
- Putting `staging` first in `baseBranchPatterns`, which starves `main` instead.
- A finite limit such as 4: revogen's queue alone was seven.
- A packageRule scoped to `staging`.

**Review.** Round 1 (Opus) found one major: the first draft promised all five branches, and the digest won't open. It also found two minors, a guard gap for a packageRule in renovate-config and an unflagged PR wave, and two nits. All were folded in. Round 2 (Opus) found only minors, all folded in. The one worth knowing: the four branches open only if the run gets to them. `writeUpdates` stops after an automerge and the job restarts once, so a run that merges a `main` group and then a carried-over `staging` PR leaves the rest for the next window. That gate predates this change.
