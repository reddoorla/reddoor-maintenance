## 2026-10-19 — axe-core 4.14 parses `none`, so the #888 fixtures plant their colour through getComputedStyle (#1514)

reddoorla/reddoor-maintenance#1491, the first lock-file PR to open here since the preset fix (`.github#38`, P1-52), went red on `build`. All 11 failures were in `tests/audits/a11y-live-spec.test.ts`.

**The cause is axe-core 4.13.0 → 4.14.0**, which came in transitively with `@axe-core/playwright` 4.13.0 → 4.14.0. Playwright went 1.62.1 → 1.64.1 in the same lockfile, so the two had to be separated. In this container the PR branch first failed nearly the whole suite, but only because 1.64's Chromium (headless shell 1248) was not installed. That was an environment artifact, not CI's failure. Once that browser was installed the count fell to 11, which matches CI. Then:

- `main` passed 63/63 (the control).
- The PR tree with only axe swapped back to 4.13.0 (a symlink in the pnpm store) also passed 63/63.

axe 4.14.0's changelog carries "color-contrast: handle `none` and exponents in color strings" (dequelabs/axe-core#5422). Every #888 fixture planted its unparseable colour as `oklch(0.205 0 none)`. On 4.14 those nodes are simply measured, so the contrast-unmeasured and rule-errored alarms had nothing to find.

**axe is right, so nothing is pinned.** A probe in Chromium 156 put 23 colour forms through axe's `Color.parseString`: `none` in each position, exponents, display-p3, rec2020, relative colour, `color-mix`, `light-dark` and `AccentColor`. It was run on both versions as its own control. axe 4.13 threw on the five known `none`/exponent shapes. axe 4.14 parsed every one. So no real CSS fixture can make axe 4.14's colour parser fail any more.

The suite already had a precedent for this situation: `FAKE_BLEND` shims `getComputedStyle` for a blend mode Chromium does not render. #1514 adds `FAKE_COLOUR` next to it:

- Elements marked `data-fake-bg` / `data-fake-fg` hand axe `color(--brand …)`, a CSS Color 5 custom colour space that both axe versions reject.
- The shim covers `background-color`, `color` and `-webkit-text-fill-color`. axe reads `-webkit-text-fill-color` before `color` for the foreground, which a first draft that faked only `color` would have missed.
- axe's own colorParse-incomplete path and thrown-rule path run unmodified.

Mutations, on #1491's lockfile:

| Mutation                          | Result                       |
| --------------------------------- | ---------------------------- |
| Shim emptied                      | 11 red, the same 11 as #1491 |
| axe 4.13.0 swapped in             | 63 green                     |
| `unparseableContrastNodes` → `[]` | 5 red                        |
| `rule-errored` push removed       | 12 red                       |

`src/` is unchanged. The generated spec resolves `@axe-core/playwright` from each site's own `node_modules`, so a site on axe ≤ 4.13 still meets Tailwind's none-hued colours. For those sites the `write 0 for "none"` remedy is still right, and it keeps its unit coverage in `tests/audits/a11y.test.ts`. One adversarial review round came back clean: two minors and a nit, filed as #1515, #1516 and #1517.

**Belief corrected:** the brief guessed `axe-core` or `jsdom`/`happy-dom`. It was axe, but not a regression. Upstream fixed the exact bug our fixtures depended on. A test that plants an upstream bug as its input is coupled to that bug's lifetime. That coupling is why the stand-in is now explicit and named.
