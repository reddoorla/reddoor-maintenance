## 2026-10-20 — OD 133: bake-off agents get a read-only type; the Bash deny it was for does not exist

Landed in the PR that carries this file. The ask and its answer are in the home base,
`reddoorla/reddoor-workspace` `decisions/2026-10-20-1642-od-133c-agent-type-cannot-deny-bash-commands.md`.

**What the brief asked for, and why.** Operator decisions 133 closed #1444 unmerged after
seven review rounds on `forbiddenCommand`, the tripwire that reads each bake-off arm's Bash
commands after the run. It chose option (c) of decision 131 instead: launch every arm, gold
and referee as a custom agent type whose permission rules deny `gh`, `git push` and
`curl`/`wget`, and stop detecting.

**Belief corrected on contact: an agent type cannot deny part of Bash.** The first build put
`disallowedTools: Bash(gh *), Bash(git push *), Bash(curl *), Bash(wget *)` in
`.claude/agents/bakeoff-readonly.md`. The probe ran the real bake-off launcher (`launchers()`,
as `split` does) from a nested `claude -p` started in the worktree, so it loaded the worktree's
agents. The arm's `.meta.json` said `"agentType":"bakeoff-readonly"`, and the arm reported no
Bash tool at all. A second run tried five variants on Sonnet `low`:

- the type as committed: `No such tool available: Bash`;
- the same `tools` with no `disallowedTools`: had Bash, and `echo` ran;
- the legacy `Bash(gh:*)` syntax: no Bash;
- `agent()`'s own `opts.disallowedTools`: no Bash;
- the default agent: Bash and every other tool.

The sub-agents docs say it in so many words ("An entry with a specifier, such as
`Bash(git push *)`, still removes the whole tool"), and the 2.1.304 bundle's tool resolver adds
the tool name of every entry, specifier or not, to the set it filters by. Every bake-off role
needs Bash: the gold and referee verify with scripts, `pnpm-update` runs pnpm, and t4 runs
`pnpm check/lint/test:unit`. That was the brief's first stop condition. It went to a decision
file and AskUserQuestion. The operator chose (a): keep the type with its `tools` allowlist
only, and keep `forbiddenCommand` frozen as the Bash check: nothing blocks a command during
the run, and a flagged one faults the arm in `score`.

**What landed.**

- `bakeoff-readonly` has `tools: Read, Grep, Glob, Bash, Write, Edit`, no `disallowedTools`, and
  no model or effort, so each launch's own still applies.
- The workflow passes it as `agentType` on all three launches.
- A test runs the workflow on a stub runtime and checks every launch. It went red before the
  wiring, and it went falsely green once: the expected value was the not-yet-exported
  `AGENT_TYPE`, so both sides were `undefined`. Fixed by comparing to the literal name.
- Another test refuses any `disallowedTools` key, with the reason.
- The re-probe inside a real Haiku `medium` arm: `echo`, `pnpm --version` (11.11.0) and
  `git log -1` ran, and `ToolSearch` was answered `No such tool available: ToolSearch`. The
  default-agent control ran the same three and got `WebFetch` back from ToolSearch.

What this buys is the MCP route: the one read-only rule a real run broke was a Haiku skeptic's
MCP call in the 2026-10-19 refute-repo run, and that call needs a tool the type does not grant:
`tools` is an allowlist by the docs, and the probe found no ToolSearch to reach one.
Bash `gh`, `git push` and `curl` are still only caught after the run.

**Also measured: settings deny rules bind a subagent.** In this session, started in the
workspace with its deny list live, a default workflow subagent was refused `rm -rf` and a read
under `~/.config/reddoor-maint/`. Same-shape controls ran. That settles #1431's item 137 (e)
precondition (posted there). It does not help here: a settings rule is session-wide, so
`Bash(gh *)` would deny the operator's own `gh`, and the docs list forms it misses
(`sh -c 'curl …'`, `/usr/bin/curl`, `git -C . push`).

**Defects found on the way.**

- The first probe's arm, the default agent on `main`'s workflow, declined all 18 commands.
  The prompt always ends with `readOnlyRules` ("Do not run gh, git push…"), and Haiku ruled
  that a workflow script had no authority to override it. The prompt layer held, but that is
  no permission-layer data; the variant run used a prompt with no conflicting rule.
- Nested `claude -p` sessions inherit `CLAUDE_CODE_SESSION_ID`. The first pair shared this
  session's id and its scratchpad rules, and both refused a `scriptPath` outside their cwd.
  `env -u CLAUDE_CODE_SESSION_ID … --session-id <uuid> --add-dir <probe dir>` fixed both.
- In the nested session even the default agent got "This command requires approval" for
  `pnpm --version`, so the worktree's `Bash(*)` allow did not apply there. The re-probe passed
  `--allowedTools Bash` to stand in for it. The tool-removal finding does not depend on it.
- One README line was wrong before it shipped. The list of tripwire forms came from the issues'
  text. Running each form through `main`'s `forbiddenCommand` showed that `&>> out git push` is
  flagged on `main`: #1486 called it a regression on #1444's branch. The other 29 forms behave
  as listed.

**What it would take to deny Bash writes.** Two routes were left for later, as their own
items:

- A frontmatter `PreToolUse` hook that refuses commands naming those words. That is detection
  again, only earlier.
- A hook that runs each arm command with no network (`sandbox-exec`, `unshare -n`). Every task
  already runs offline, so that is complete.

Both are skipped in an untrusted folder and need proof on the laptop.
