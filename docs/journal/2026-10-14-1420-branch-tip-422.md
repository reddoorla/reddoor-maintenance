## 2026-10-14 — The protection audit reads a not-yet-created Renovate branch as "no branch" (P1-50)

The 10-14 06:16Z `fleet-security` run printed `PROTECTION_AUDIT gaps=15`, two more than on 10-13. Both new gaps were whole-repo probe failures, alamo-anatomy and vida-legacy-foundation, each `No commit found for SHA: renovate/staging-major-vitest-monorepo (HTTP 422)`. The audit's blocked-branch check asks `branchTip` for the tip of every branch the Dependency Dashboard names, and a branch that no longer exists was always meant to be skipped ("a stale dashboard"). `branchTip` only recognised that case as HTTP 404, so the 422 threw, the repo's catch turned it into `probe failed`, and every other check on those two repos went unreported with it.

**Measured before the edit** (~14:10Z, vida attached with `add_repo`, REST through `gh api`): `commits/renovate/staging-major-vitest-monorepo` answers 422 "No commit found for SHA"; so do `renovate/zz-nonexistent` and the slash-free `zz-nonexistent`. `GET branches` lists `renovate/major-vitest-monorepo` and no `renovate/staging-*`. So 422 is GitHub's ordinary answer for a ref that resolves to nothing on this endpoint. The existing test that pinned "a deleted branch is null" used a hand-written 404 stderr, which is why it never caught this: the fixture encoded the belief, not a measurement.

**The fix** returns `null` for a 422 whose message carries "No commit found for SHA", as for a 404. Every other 422 (a "Validation Failed", say) still throws, and so does the phrase without the 422 status. The regression test replays vida's exact stderr through `makeGitHub` and on through `resolveBlockedBranches`, the path `collectProtectionCoverage` uses in production.

**Mutations** (each turned a test in `tests/github/gh.test.ts` red): dropping the 422 case; accepting every 422; dropping the status check and matching on the message alone. The first run of M2 and M3 was void: the mutation script restored the file with `git checkout`, which put back the index copy, i.e. the unfixed code, so both "failed" against no fix at all. They were rerun by copying the saved fixed file, and each failed on the test meant to catch it.

**Still open.** The fix reaches the nightly on merge (the workflow runs `node dist/cli/bin.js` built from `main`), so the proof is the next `fleet-security` run's `PROTECTION_AUDIT` no longer listing either probe failure. That result goes in a later entry.
