## 2026-10-12 — `contrast-unmeasured` names Tailwind's `black/<alpha>` and its fix (P1-31)

The gate's remedy for `oklab(0 none none / 0.1)` was "write 0 for none in the oklab() token". There is no such token in anyone's source. The colour is lightningcss's fold of Tailwind v4's `black/10`, which is written `color-mix(in oklab, #000 10%, transparent)` when black is inlined. reddoor-website#260 found that by hand on 10-05. The remedy now names that source and says to define black as `oklab(0 0 0)`, which renders byte-identical (#260's sha256 screenshots).

**The fold, measured with `lightningcss.transform`.** Versions 1.32.0 and 1.33.0 behave the same, so the backlog's "1.33.0" was a version detail, not the cause. `#000`, `black`, `rgb(0 0 0)`, `hsl(0 0% 0%)`, `color(srgb 0 0 0)` and `oklch(0 0 0)` all fold to `oklab(0% none none/.N)`, and to `oklab(0% none none)` at 100%. Only `oklab(0 0 0)` folds to real zeros. `#111`, `#222`, `gray` and white fold to tiny floats such as `5.96046e-8`, never `none`. So the shape is exactly L = 0 with a and b both `none`, and that is what the new branch matches. An `oklch(0 0 0)` black would not have helped, which is worth knowing before someone tries it.

**Which sites it reaches: a belief corrected on contact.** The brief said "starter and starter-blux first". They are not affected. All 23 Turso sites with a `git_repo` and the three starters were built from their default branch and grepped for `oklab(0% none none`. The grep was proven on both sides first: reddoor-website `main` folds nine values, which matches #260's own count, and #260's head folds none. Only **erp-industrial** folds (`bg-black/60` in `BgVideo.svelte`, with `black: '#000'` in a `tailwind.config.js` read through `@config`). The starter family writes `@theme { --color-black: black }`, so the utility keeps `color-mix(in oklab, var(--color-black) 50%, transparent)`, and lightningcss cannot fold a `var()`. Whether the browser then produces `none` was an open question, so I probed it in headless Chromium with axe-core 4.13.0. The folded literal computes to `oklab(0 none none / 0.5)` and axe leaves it `colorParse`, which is the positive control. The var mix, `#000` mix and literal `black` mix all compute to `oklab(0 0 0 / 0.5)` and are measured. The trigger is therefore an inlined black (measured for a JS config; `@theme inline` should inline the same way [I]), not `black/<n>` alone. A static grep of the sites (`black/<n>` present plus black defined as sRGB) would have listed about 15 sites. The build listed one.

**Tested.** The new test pins four spellings: Chrome's `oklab(0 none none / 0.1)`, the minified `oklab(0% none none/.5)`, the alpha-less form, and an upper-case `0.0` form. It also pins the full `contrastUnmeasuredHelp` line, and checks that `oklab(0.5 none none …)`, `oklab(0 none 0 …)`, `oklab(0.05 none none)` and `oklch(0 0 none)` keep "write 0 for none". Of the first eight mutations, seven went red. The survivor dropped the end-of-string anchor. The adversarial review then found that the start anchor was untested too, and that the serialization test never called the new branch on the revived function. Both now have tests, and nine mutations all go red. The review also made the wording less certain: the remedy now says "most likely" Tailwind's `black/<alpha>`, because a hand-written `color-mix(in oklab, black 50%, transparent)` folds to the same value. It also moved the Operator decisions line onto its own docs-only PR, per the asking rule.
