The prospect-audit daily cap now binds on a burst, not only on a slow serial batch (#907). It used to count rows that `prospect-audit` wrote at the very end of a run, after the money was spent, so every run was invisible to the cap while it ran and any number of concurrent starts all passed the same count. Now a `running` row is reserved before anything is spent, by a single conditional INSERT that counts and writes in one statement, and the run finishes that same row as `complete` or `partial`. The cockpit reserves at dispatch, and the job it dispatches claims that reservation by site rather than taking a second slot. The cap counts finished rows plus `running` rows inside the 24-hour window. A `running` row older than two hours, which is past the private runner's 30-minute step timeout plus setup and one queued run of the same URL, is treated as a crashed run and stops counting. A run whose pipeline throws before spending gives its slot back. A reservation that meets `SQLITE_BUSY` is retried rather than treated as an outage. The cap (25) and its unit are unchanged, and the refusal now reads "audits have been started". A running audit shows as "Running" (or "Did not finish" past the stale window) on `/audits`, with no report link. Its token returns 404 from `/api/audit-report/:token` until it finishes. Migration `0029` adds `prospect_audits.claimed_at`.
