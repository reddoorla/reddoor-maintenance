`prismic-ci` now resolves a positional checkout, and `launch` refuses to draft while a site's matching twin is live.

`reddoor-maint prismic-ci <path>` always failed with "no Git repo on this site": the positional inventory provider builds `{ path, name }` and nothing else, and the recipe read `site.gitRepo` directly. A site being bootstrapped is exactly the case with no Airtable row — `--fleet airtable` filters `building` and `launching` out — so the positional path was the only one `/new-site` could use, and it did not work. `resolveOwnerRepo`, extracted from `self-updating` and now shared in `src/util/git.ts`, derives `owner/repo` from `origin` when no explicit identity is set, and still throws rather than passing a malformed one to `gh`. A missing origin is not malformed: that returns `null`.

Both callers now report that `null` honestly. The old note — "no Git repo (set Airtable 'Git repo' or add an origin remote)" — asserted that no repo existed and prescribed two dead ends for a reachable case: an origin of `git@github.com:espada.git` (owner omitted) resolves to `null` without throwing, and the operator has an origin remote and, being pre-launch, no Airtable row. Both callers now say the identity could not be **determined**.

Worth stating plainly, because it changes who gets written to: the origin fallback is **unconditional**, not confined to the positional path. An Airtable row with a blank `Git repo` cell used to hard-fail; on a `--fleet airtable` run it now derives an identity from whatever `origin` the local checkout happens to carry, and can open a PR against that repo.

`launch` gains two disposition steps. `matching-disposition` runs first, on the filesystem: a checkout carrying `src/routes/dev/match` without a dev guard stops the chain before any GitHub write. Three placements count, most-preferred first — `src/routes/dev/+layout.server.ts` (the fleet-wide class-fix for "dev routes ship in production", whose `load` runs for `/dev/match/[uid]` too), then the `/dev/match` layout, then `[uid]/+page.server.ts`. The refusal — `error(404` or `throw` — has to be the `if (!dev)`'s own consequent, read out of source with comments stripped and string contents masked; a refusal that merely occurs somewhere else in the file, or only inside a string, is not a guard. The comment stripping is a scanner: it removes line and block comments, so the common commented-out guard cannot pass, but a regex literal containing a quote character defeats it, and that shape is refused rather than accepted only because the masking pass misreads it the same way.

The step also needs positive evidence that the path it was handed is a checkout at all. `src/routes` must exist before a missing `src/routes/dev/match` may be read as "this site has no twin": a path never cloned, a stale clone, a mistyped site name and the wrong working directory all produce that same absence, and `resolveSites` builds the path with no existence check. Its passing message names what it observed, source text, not the runtime behaviour it cannot see.

`dev-guard` then runs against the DEPLOYED url. `/dev/match/home` must answer 404 with this site's own error page, and `/health` must answer 200 as a liveness control, so a dead host, a wrong url or a parked domain fails before the 404 can be read as evidence. Two hardenings worth naming: the unguarded twin answers 404 for any uid missing from its assembly map, rendered through the same error page — so on a site whose uids lack `home` the check could never fail. A deny clause on the route's own "no assembly for" message closes that; it only ever refuses, never grants. And the probe is timeboxed at 15s — the same deadline as `audits/netlify-deploy.ts`, `github/gh-rest.ts` and `prismic/models/remote.ts`, though not a house constant: `audits/function-health.ts`, `audits/form-e2e.ts`, `audits/browser.ts` and `prospect/dns.ts` use 10s, `prospect/ownership.ts` 12s and `prospect/crawl.ts` 20s.
