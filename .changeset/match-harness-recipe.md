New standalone recipe: `reddoor-maint match-harness [site] --ref <url>` installs the matching harness — the `/dev/match/[uid]` route, the `matching/` gate scripts and their one read layer, the site records, and the `.gitignore` / `.prettierignore` / `CLAUDE.md` blocks — in a single commit on its own branch.

It is not part of `init`. A harness needs a live reference to gate against, and `--ref` is required for exactly that reason: a harness with no reference can only ever report an absence of errors, so the recipe refuses rather than installing something that would go green on nothing. `--cand` and `--matrix` override the SvelteKit dev server and the fleet's 1440 / 834 / 390 breakpoints.

**Everything specific to a site is data.** `matching/harness.json` holds the page table, the two hosts, the matrix, the threshold and the reference marks; `matching/harness.mjs` is the only thing that reads it and the only place the skill path is written down. That split is the whole point of the recipe. On the site it was cut from, the page table, the two hosts, the matrix and the skill path had been hand-copied across the harness one script at a time — a table that goes stale the moment an anchor list changes, and a wrong denominator makes the score a lie in the flattering direction. After the consolidation exactly one of that site's scripts still carries a hand-typed copy of the full nine-row table (measured on `main`: `matching/probe-chrome-count.mjs`), and everything the recipe itself installs reads the table from `harness.json`. Edit `harness.json`; never `harness.mjs`.

**Records are never rewritten.** Files a site authors — `harness.json`, `LEDGER.md`, `floors.mjs`, `census-deviations.mjs`, `spec-sections/`, `site-pages.js` — are install-if-absent and are not touched again. Recipe-owned scripts are byte-compared: one still matching a previously shipped render is safe-replaced; one that has been hand-edited is FLAGGED in the notes and left alone, so an operator's change is never silently reverted and never silently kept as though it were ours. CRLF and trailing whitespace are the only differences that still count as ours.

The recipe hands the site's prettier only what the site owns (`src/` and `CLAUDE.md`). The harness code ships template-verbatim and is in `.prettierignore`: a site whose `printWidth` differs would otherwise reformat every recipe-owned script on install, and the byte-compare that makes the next upgrade possible would then flag all of them as hand edits. The Markdown stubs are not formatted on install either, so they are authored prettier-clean and there is a test that proves it — they stay inside a site's own `prettier --check .`, and an unformatted stub would turn the first `pnpm verify` after install red.

Also worth stating, because the `.prettierignore` block looks over-specific: it ignores `matching/*.mjs`, `matching/*.sh` and `matching/harness.json` rather than `matching/`. **eslint does not lint Markdown**, so for `SPEC.md`, `LEDGER.md` and `spec-sections/` prettier is the only style check there is, and a blanket entry would leave the records with none. The comment shipped in that block previously justified the narrowing differently — "eslint already ignores this whole directory (eslint.config.js:52)" — which is true only of the one site the recipe was cut from. The eslint config this package writes (`src/configs/eslint.ts`) contains no `matching/` entry at all, so on every site the recipe installs into, that reason was false while the conclusion stayed right. Corrected here; whether the recipe should also install an eslint ignore is open in reddoorla/reddoor-maintenance#730.

Three of the new tests shell out into the installed site rather than comparing bytes, because a recipe that copied a working harness and a recipe that copied a broken one are byte-identical from the outside. `matching/next.mjs` must refuse an empty corpus with "no parseable gate run" and exit 2 rather than print `SCORE 0/0`; `matching/gate.sh` must refuse the seeded reference because `refMark` ships empty — the fail-closed default, since a fresh install cannot produce a score until someone names a string only the reference serves; and once a verified reference answers, the same command must get past `--check-ref` to the Phase 1 refusal, `REFUSED: no '## home' section in matching/SPEC.md`. The last two both exit 2, which is why each asserts on its own message and on the absence of the other's.

**An install git did not take is a failure, not an "applied".** The recipe writes 17 files plus three appended blocks and commits with `git add -A`, which honours the site's .gitignore and exits 0 either way — and git cannot re-include a file whose parent directory is excluded. A site that already ignored `matching/` therefore got 13 of the 20 installed paths on disk, none of them in the commit, and a result of "applied": a `/dev/match` route, a `site-pages.test.ts` and 83 lines of CLAUDE.md rules naming `matching/gate.sh`, `matching/next.mjs` and `matching/harness.json` that existed on the operator's machine and nowhere else. The recipe now asks git what actually landed — every installed path must be FOUND in `git ls-tree -r -z --name-only HEAD` — and refuses otherwise, naming each absent path and the `<file>:<line>:<pattern>` that excluded it. The check runs over the whole manifest, not this run's writes: where the files are already byte-correct on disk the run writes none of them, so a delta check would pass over a commit containing none of them. Before returning, everything the run wrote to a refused path is put back as it was, so a refusal leaves the checkout byte-identical to how it found it. A pre-write ignore check was tried and rejected: a site ignoring `*.sh` or `*.mjs` installs correctly, because the block's own `!matching/*.sh` / `!matching/*.mjs` come after the site's rule and the parent directory is not excluded — checking before the block exists would refuse two working configurations.
